# Furnishes 软件与服务全量规划

2026年10月2日讨论总文档

Furnishes 的核心业务是销售真正能交付、使用和持续扩展的模块化家具，并帮助用户判断这些家具怎样适合自己的生活和空间。软件把需求梳理、现成商品选购、房间搭建、家具配置、AI 辅助设计、方案比较、购买与后续调整连接起来。传统家具和用户已有家具是理解真实房间的重要背景，也可以参与生成与摆放；它们不能因为主营模块化家具而从场景中消失。
用户可以直接买一件现成家具，也可以从生活困扰、灵感图片、房间尺寸、现有家具或一个模糊想法开始。Project 让这些探索可以保存、回来继续，并同时保留不同方向。Eva 是贯穿网页的助手：理解当前任务，记住适用范围，帮助用户慢慢选择，并在需要时推进到可配置、可验证、可购买的结果。
本文覆盖本次聊天从最初项目理解到六个参考产品研究的全部主题。正文按业务与用户操作重新组织；末尾有逐轮覆盖索引、来源目录与待确定事项。配套聊天正文存档保留历史问答原文，便于追溯详细表述。
阅读时区分四种状态。已确定要求来自你的明确表达；现有实现来自所提供代码、文档或本次观察；建议方案是讨论中提出的可行做法；待验证表示尚不能确认实现、效果或商业条件。文中的建议按钮名称和页面归属用于解释操作逻辑，不代表已经批准的最终视觉设计。

# 1 商业服务与产品边界
## 1.1 用户买到的是什么
用户最终买到的是能解决具体使用需求、适合自己房间的家具及相关服务。模块化应首先表现为成品好看、好用、尺寸与功能合适；之后才是能够继续加、换、移动、修复和重新组合。不能把用户是否愿意经常拆装当作产品成立的前提。
产品范围可以包括一个小配件、一件家具、一个工作区、几件家具组成的角落，以及整个房间的组合。业务不应被收窄为“做一个测评，再推荐某种小柜子”，也不应只剩下漂亮的 AI 效果图。完整方案可以是一个具体场景的解决办法，但用户仍有权只购买其中一件。
房间中的传统沙发、床、餐桌等提供比例、风格、生活方式与空间限制。即使它们不是 Furnishes 的销售商品，也需要在房间里存在。生成流程应支持传统家具与模块化家具共存；模块化结构如何实际组合属于进一步的产品与工程规则，不能用一个视觉相似的 AI 网格代替。
## 1.2 服务可以从不同位置开始
第一种入口是明确购物。用户已经知道自己要一个边柜，从商品列表进入详情，选择有效配置，然后直接下单。无需先填写测评、创建房间或和 AI 对话。
第二种入口是自己设计。用户来到 DIY 或 Playground，快速搭建大致房间，放入现成家具模板，移动、旋转、换颜色或调整某一块板件。需要帮助时再叫 Eva。
第三种入口是语言描述。用户告诉 Eva 家里是 2b2b、面积以及各房间长宽，或者说“给我一个放咖啡机和杯子的家具”，系统根据已知信息建立初稿，缺少影响结果的尺寸时再补问。
第四种入口是生活问题。用户通过短 quiz、聊天或上门沟通说明杂乱、收纳不够、工作区难用等困扰；系统帮助梳理需求，给出方案，用户选择后再生成或配置家具并安排到房间里。
第五种入口是纯探索。用户只是喜欢一个颜色、想试试新风格、给父母家看看、收藏一个未来想法。这些都是真实需求，不能被强制解释为本人的长期审美或马上购物的意图。
## 1.3 三阶段服务图的含义
“生活小麻烦 → 一套家具系统 → 好看、好用、可继续加”表达了从问题到可用结果的服务过程。中间展示的家具系统和右边房间中的家具，应当可以对应到同一组实际配置、组件和数量；不能只是两张风格相似但无法兑现的图。
用户同意的是某个解决方向，例如玄关整理与工作角整合。随后可查看家具、组成、空间效果、价格与交付方式。图片中的配件和生活物品应区分随货内容、可选加购和纯示意陈设。
这条路径合理，但不是全网站唯一的强制流程。直接购物、从已有房间继续改、只试一种颜色，都应该保留短路径。
## 1.4 现阶段怎样如实表达服务
如果当前实际过程是团队上门了解需求、人工整理方案，配合 visualization 和 AI 推荐摆放，就应这样表述。可以说“我们了解你的需求，使用空间可视化和 AI 辅助建议，一起找到适合的家具方案”。不能把人工完成的测量、设计、校核和交付描述成已经全自动完成。
“AI 生成一个好看的方案”“可编辑的空间模型”“可以制造的模块化配置”“可直接购买的商品”是四个不同结果。营销、界面和内部交付标准需要区分它们，避免用户以为屏幕里任何模型都可以按显示价格购买。

# 2 软件的整体服务链
## 2.1 从探索到交付的连续过程
完整过程可以是：发现需求或商品，收集条件，形成候选方向，在真实或近似空间里尝试，选择具体家具配置，检查尺寸与兼容性，确认购买清单，下单交付，回到 Project 继续使用或扩展。用户不必按固定顺序走完每一步。
例如用户已经在商品详情确定颜色，可以先购买，再建立房间考虑下一件；用户已经有房间，也可以在其中随意探索而不购物。内部需要有清楚状态，用户不需要逐个确认所有状态。
## 2.2 三种软件资产不能混为一体
主站 furnishes_prod 含测评、聊天、偏好、Project、Room Plan、Design Brief 和商品交易等多条能力线。提供的代码里能看到这些模块，但存在独立的数据对象、功能开关和衔接边界，不能因为都在同一仓库就认为已经串通。
当前 furnishes-playground-standalone 是从主站抽出的房间与家具工作区，便于独立运行和验证。它有空间画布、对话、生成、局部编辑、项目存储等基础，也有本地接口替代部分主站依赖。它不等于完整生产商城。
家具页面连续探索原型及其执行文档，描述的是商品体验和组件复用方向。原型里的 SVG、组合数据和测试结果，不等于这些能力已经在主站商品详情或 Playground 中完整上线。
## 2.3 需要贯通的信息
用户从 quiz 到商品、从商品到房间、从房间到购物车，应携带当前 Project、房间、所选方案、商品配置、来源以及必要的需求摘要。不能每换一个页面就重新问预算和房间尺寸，也不能用一个全站“最近打开的项目”随意接管不同浏览器标签页。
从结果返回来源也同样重要。看完详情回到列表时保留筛选与滚动位置；从商品详情进入房间后能返回原商品；从历史方案返回编辑时能找回最新工作稿；从订单回来能看到当时购买配置和现在方案的差别。

# 3 用户对象与状态应如何理解
## 3.1 Project 不是一次性展示页
已确定：用户的需求、探索和决定应组成可保存的 Project。Project 可以再次打开继续看、继续聊、继续设计。它应关联房间、候选家具、需求记录、测评结果、不同想法、保存版本，以及相关购买记录。
建议的对象关系是：账号下有多个 Project；Project 下有房间；一个房间可以有多个方案；方案包含家具实例；家具实例引用具体商品配置或概念模型；模块化家具再包含组件。实际技术结构可以共享数据，但用户不需要学习这套层级才能使用。
一个聊天会话不等于一个 Project。开新聊天不应自动丢掉当前房间；建立一个新想法也不必复制整个家。新聊天、新方案、保存版本和复制 Project 必须分别表达清楚。
## 3.2 家具至少有六个独立属性
家具类型回答“它是模块化家具还是传统家具”；来源回答“来自商品库、上传、照片识别还是 AI 生成”；所有权回答“用户已有还是准备购买”；可编辑性回答“可改位置、材质、组件还是只能看”；可购买性回答“有有效商品配置、需要询价还是仅作概念”；锁定状态回答“此次允许 AI 改动什么”。
这些属性不能合并为“自己的”和“系统生成的”两类。例如 AI 从用户照片重建的沙发，来源是 AI 重建，所有权却是用户已有；从商品库选出的模块化柜子也可能已经被用户购买。已有家具可以允许移动，新商品也可以被锁定。
界面默认只显示影响当下操作的标识。选中一个物体时，再显示来源、拥有状态、可购买状态与锁定范围。不要让整个房间长期堆满标签。
## 3.3 候选和决定必须分开
喜欢一张图、收藏商品、把家具放进房间、采用一个方案、加入购物车、完成下单，含义不同。心形收藏不应自动替换房间家具，拖入场景不应自动购买，生成一套方案也不代表用户认可其中全部家具。
这些状态需要在数据中清晰存在，但不能把它们全部变成每次必点的一排按钮。用户只想试颜色时即时预览加撤销即可；用户明确点击有效商品的加入购物车时，不应再绕回冗长设计流程。

# 4 页面之间的操作逻辑
## 4.1 首页和发现入口
用户可以从商品、设计空间、灵感或“帮我理清需求”进入。已有 Project 的用户应能直接继续最近相关的项目，而不是重新接受一次 onboarding。入口名称可以再设计，但必须让购物与探索都成立。
如果用户先做 quiz，结果应能先看，再在保存到账号时说明登录价值。不要让用户回答完所有问题才突然发现必须注册才能看到任何结果。匿名探索与账号同步如何实现仍需具体产品政策，但要保住已经输入的内容。
## 4.2 商品列表和商品详情
商品列表负责浏览、筛选、比较与进入具体商品。商品详情负责解释商品能做什么、尺寸、组成、颜色与材质、价格、交付和拼装，以及购买与放进房间两个方向。
“放进我的房间”应携带已选配置。已有明确当前房间时直接进入它；存在多个合理目标时再轻量选择。不能无提示新建空房间，也不能忘掉刚选的颜色。用户仅看一个现成家具效果时，不应被迫学习完整建模系统。
## 4.3 Project 页面
Project 列表用于找回项目、看预览、名称和同步状态，并支持复制。Project 内部汇总当前房间、想法、未解决问题和已保存方案，但不必另造一套复杂管理后台。
用户返回时最有帮助的是“上次看了两种柜子，还没有决定尺寸”，以及直接继续对应位置。AI 不应自动把旧目标当作今天唯一任务；用户可以说“今天先看看卧室”，原来的玄关讨论仍保留。
## 4.4 Playground
Playground 是空间与家具决策的工作区。用户看房间、放家具、选择对象、直接编辑、向 Eva 表达局部需求、查看动线、进入第一人称、比较方案并保存。它不是所有全站页面功能同时展开的容器。
从画布里打开商品资料，尽量保留房间上下文。只有确实需要更完整资料时才进入详情页，并提供返回位置。组合、拼装、单品查看是同一工作区里的临时任务，完成后回到原相机和原选择。
## 4.5 购物车和订单
购物车展示真实选购的配置、数量、价格与服务条件。场景里的全部物体不能自动进入购物车；传统参考家具和用户已有家具不计入购买。付款后订单配置应固定，之后的房间试验不应改写订单。
购买后 Project 继续存在。它可以保存家具配置与兼容关系，帮助以后扩展、搬家、调整或补买。但能否按差额购买、旧件是否兼容和是否能重新使用，都需要产品规则确认。

# 5 Quiz 是一次探索而不是给用户定型
## 5.1 Quiz 放在哪里
建议全站保留一个可独立进入的需求或灵感探索入口；进入 Project 后，quiz 也可以从 Eva 或当前房间打开。二者使用同一套问题和结果结构，而不是两套互不相认的测评系统。
简单问题适合在对话旁直接用选项卡回答，例如主要使用者、最烦的事情、预算区间。需要图片比较、成组选择或较多题目时，打开集中填写的测评界面。完成后回到原 Project、原房间与原任务。
用户喜欢聊天就通过自然语言回答；希望更快就点选。聊天已经提供的信息应被带入，不能为了“完成表单”强迫再填一次。重要信息可以显示为可修改摘要，而不是默默推测。
## 5.2 同一个用户可以反复做出不同结果
已确定：测评可能只属于这一次、这个房间或某种尝试。新结果不能自动覆盖整个用户，也不能强迫所有房间统一风格。每次测评应该有独立记录，保留回答、结果、适用目标和是否被采用。
例如第一次测出温暖木色，第二次试冷静工业风。第二次可以形成新候选方向，原方案仍存在。用户说“这只是看看”时，不更新已采用方向；说“这次书房就用这个”时，作用于书房当前方案。
## 5.3 结果如何推进
结果页应解释与用户选择直接相关的建议，例如工作区需要桌面深度、玄关需要随手放置和鞋物收纳。风格标签只能帮助组织灵感，不能替代真实功能和尺寸判断。
用户可以只保留结果中的一部分、调整一个答案、查看具体家具，或者让 Eva 把方向放入房间。拒绝某个结论后应修改对应假设，无需整份重做。预算、尺寸、已有家具等明确事实，应与算法推导的风格倾向分别保存。
## 5.4 当前代码的边界
主站 quiz 结果合同可以见到主次风格、颜色、生活方式推导、房间关注点、预算和推荐信息，但不能据此假设所有原始回答、家庭条件、门窗和尺寸都已完整传给 Playground。
现有 quiz ingestion 把部分结果映射成偏好候选，并非直接自动确认全部长期记忆。后续需要补的是测评会话的适用范围、探索状态、是否采用，以及跨页面使用时的上下文，不是简单把结果永久写入用户档案。

# 6 Eva 应该怎样陪用户慢慢选择
## 6.1 助手的角色
Eva 应贯穿浏览、思考、比较、空间调整和购买。它需要知道用户正在看的页面、Project、房间、方案和选中对象；记录用户为什么犹豫、为什么排除某个选项，以及下一步缺什么信息。
“陪着慢慢挑”不等于不断主动插话。多数时候，助手应安静地保留上下文，在用户表达需求或遇到真正阻碍时提供有用下一步。用户切到手动操作、关闭聊天或暂时离开，都不应损坏正在进行的探索。
## 6.2 对话和操作是一条连续路径
用户说“这个柜子太高”，如果已选中一个柜子，Eva 应明确绑定它，并结合配置能力给出可执行选择。若降低高度会减少一层，应说明功能和价格影响；如果模型不能参数化，就不要假装它已经变成可制造配置。
用户说“我不知道房间哪里不对”，Eva 可根据目前布局、已知尺寸和生活需求提出有限的诊断。用户接受一个方向后，系统再形成预览。不要一开始连续问十个问题，也不要为了显得主动生成整套无关家具。
用户说“先记着以后做咖啡角”，Eva 应记录想法，不跳页、不重排房间、不自动开始付费生成。用户问尺寸或材质时，应先回答问题，不把每一句都理解为设计命令。
## 6.3 Agent 的合理能力边界
这个软件可以描述为带有 agentic workflows 的 AI 辅助家具与空间设计平台。当前已有结构化生成和工具流程，不代表所有任务都由完全自主 agent 完成。真正可依赖的操作闭环需要理解目标、调用工具、校验结果、呈现变化、应用或撤销，并报告失败。
建议 AI 工具围绕明确对象工作，例如创建房间、放置商品、修改一组物体、生成候选布局、检查碰撞、计算有效配置、准备购物清单。视觉模型生成、空间验证和商品系统应各有结果状态，不能让聊天文本替代真实执行。
## 6.4 哪些操作直接做 哪些操作先预览
颜色、位置等低影响且可撤销的明确操作，可以直接反映并提供撤销。替换商品可以在一轮连续预览中反复比较，最后采用或退出，不必每换一个都弹确认。
改变整个布局、涉及多对象或可能破坏已有决定的操作，应先显示具体变化和范围，再应用。实际购买、覆盖固定保存版本、删除 Project 等具有不同后果的操作，需按其风险提供明确行动，不应与一般试试看混在一起。
## 6.5 AI 不确定时怎样回应
缺少尺寸时允许先探索，但要保留“估算”属性；涉及能否放下或制造时再补测量。无法匹配现成商品时说明是概念或需要询价。生成失败应保留原方案和已成功的部分，给出重试或替代路径，不能用一条“已完成”掩盖失败。

# 7 记忆的范围与性质
## 7.1 四个独立判断
第一是范围：全局用户、某个 Project、某个房间、某个方案或某件家具。第二是性质：事实、偏好、限制、灵感、试验或已作决定。第三是确定程度：系统推测、用户提到、正在考虑、明确确认。第四是有效性：当前有效、临时、已被替代或用户撤回。
保存很久的信息不一定全局适用。例如妈妈家的尺寸可以长期留在那个 Project，却不应该影响用户自己家的家具；一次被保存的大胆配色方案也不等于用户今后都喜欢该配色。
建议同时保留信息来源、时间和相关讨论。这能解释为什么 AI 给出某个建议，并在新旧内容冲突时找到依据。内部字段不应变成用户每发一句话都必须填写的分类表。
## 7.2 作用范围的默认规则
优先采用明确的当前目标和用户最新指令。正在书房方案里讨论的“这次想用黑色”，默认属于该方案；“我一直不喜欢玻璃桌面”可以成为长期偏好候选，但不应强行阻止用户之后试玻璃。
当前选中对象、房间和来源入口可以帮助限定范围。只有不同解释会造成实质差别时再追问，例如“这是给妈妈家，还是替换你现在书房的柜子”。多数情况应通过可见对象标签和简短回述让用户容易纠正。
## 7.3 记忆冲突与修改
旧偏好和新要求冲突时，当前明确要求优先。AI 可以提醒一次相关背景，但不能反复把用户拉回旧选择。删除一个方案不必删除所有一般偏好，回看旧版本也不能倒退整个账号的记忆。
合住者或伴侣参与时，应保留意见属于谁。多人协作是可扩展方向，本次没有证据证明已经完整实现；至少不能将一个人的测评无提示覆盖另一人的意见。
## 7.4 当前记忆基础
主站已有偏好提案、Project 记忆和聊天工作流相关设计。Project 记忆文档描述了摘要、时间线、已确认偏好、房间尺寸、推荐标题和会话摘要等上下文，并存在功能开关。它并不等于已经实现跨页面、跨方案、对象级别的完整 Eva 记忆。
需要补齐的重点是作用范围、推测与确认的区分、用户纠正入口、不同方案互不污染，以及只向 AI 提供当前任务所需信息。保留所有原始聊天并把全部内容塞进每次提示，不是可靠的长期记忆设计。

# 8 多个想法同时存在时怎样工作
## 8.1 四种不同的想法
一个随口提出的灵感可以先是笔记；同一位置上的两个柜子可以是候选对比；同一房间的不同布置可以是方案分支；另一套房子则通常是另一个 Project。系统需要分清这些，用户不必每次先回答“我要创建哪一种对象”。
“再看看绿色”通常是临时预览；“这个方向也留着”才需要保存为可返回的方案；“妈妈家也要做”意味着切换或建立独立项目。AI 应根据话语与当前操作选择最轻的合理动作。
## 8.2 不让比较变成叠加
用户比较两把椅子时，不应默认把两把都放在同一个位置，也不应自动增加购买数量。替换预览和同时摆放是不同动作。如果用户确实想要两把，再以明确数量反映。
用户喜欢 A 的布局和 B 的柜子时，可以将 B 的柜子复制到 A，其他内容不动。必须复制有效配置并形成独立实例，不能让以后在 B 改色时 A 也跟着变化。
## 8.3 不让保存打断探索
用户可以继续做当前事情，同时保留一个稍后再看的想法。AI 的记录应轻量可找回。不要每条灵感都跳到一个空白 Project，也不要将聊天列表当作方案列表让用户猜哪一条对应哪一个房间。
当前画面必须让用户知道正在编辑哪个 Project、哪个房间、哪个方向。方案名可以自动给出可编辑描述，例如“靠窗工作区”，但不能依靠一长串自动生成时间戳作为唯一识别方式。

# 9 房间创建与照片输入
## 9.1 手动搭建房间
你的目标是让普通用户用很少步骤建立房间大小与布局，接近 CAD 的直接操作，但不要求理解专业 CAD。建议先选或画轮廓并输入主要尺寸，再补门窗与需要保留的家具；不规则房间可以继续编辑，而不是只能选矩形。
系统应保留真实轮廓、单位和尺寸来源。只把网格输入转成一段文字，会丢失精确几何关系；面积和外接矩形也不足以表达凹角、走廊与开门位置。
## 9.2 用语言创建
用户描述 2b2b、总面积和各房间长宽，可以得到初始结构。户型名称只提供数量或类别，不能推断准确连接关系、门窗和比例。生成结果应允许用户快速调整，并标识哪些尺寸来自用户、哪些来自估算。
用户可以只先建一个房间，不应因全屋信息缺失而无法试一件家具。只有开始比较实际通行或准备购买时，相关尺寸才需要更严格核实。
## 9.3 一张照片能做到什么
今天讨论的关键区别是：上传图片作为风格参考、把一个物体变成近似 3D、把整间房重建为多个可编辑对象，是不同功能。当前流程有图像参考与单物体 image to 3D 的基础，不能据此承诺完整照片房间已经可准确还原。
可行的初步方案是识别可见家具与墙地面，拆分对象，结合用户提供的一项尺度或房间尺寸建立近似场景，允许纠正类别、大小与位置。单张图通常不能可靠知道隐藏面、遮挡后的物体、真实厚度、背面结构或完整房间拓扑。
需要更可信的还原时，应加入多角度照片、平面图、测量或扫描。重建一件模块化家具的外观，也不代表识别出了真实板件、连接方式、承重和商品编号。
## 9.4 开发与运行费用的讨论边界
此前聊天给过条件性估计：复用现有生成、场景和对象编辑基础，近似照片重建原型可能需要一至两周；较可用的 beta 可能需要四至八周。它们不是排期承诺，取决于识别质量、供应商接口、编辑范围和验收标准，宜先用十至二十张真实照片验证。
历史答复还引用过 SAM 3D 的单计费单位约 0.02 美元，以及某 Hunyuan 快速模型含 PBR 约 0.375 美元每物体；八个物体仅该模型调用算术约三美元。这些是当时讨论的价格信息，本文件不把它们当作当前有效报价。一个房间的实际成本还包含分割、语言模型、重试、素材、存储和服务成本。
“便宜 enough”需要同时看生成次数、失败重试、等待时间和可销售转化。看起来便宜的网格生成，如果每次都需要大量人工修正，完整服务成本仍可能很高。

# 10 选中对象与局部 AI 编辑
## 10.1 选择整件家具
点击家具后，应出现稳定的轮廓高亮或清楚的选择状态，并显示名称。Eva 输入处同步显示当前目标，例如“书房边柜”，用户可以直接说“这个矮一点”。选中不能只靠颜色变化，也不能只在一个远处面板中暗示。
相机移动、鼠标悬停、打开聊天或查看商品资料，不应无意取消目标。清空选择、改选或切换房间后，目标变化要可理解。点空白是取消选择还是操作相机，应统一规则。
## 10.2 进入某一块板件
默认选择整件家具，进入“组成”或“编辑部件”后才选择板件或附件。层级路径可以是“书房 → 边柜 → 左侧板”，让用户能回到整件。部件列表点击与画布高亮互相对应，避免用户不知道列表里的“板件 03”是哪块。
对某块板改色，应清楚作用于单块、同类全部还是整件。结构性修改要交给配置规则验证；不能把一个视觉颜色控件误当成可以任意改变材料和承重的自由编辑。
## 10.3 一次选择多个对象
应提供明显的多选入口，桌面可以补充 Shift 点选和框选，触屏也要有等价方式。选中后显示数量与可移除的目标项，例如“书桌、边柜、推车，共三件”。AI 收到的是明确的对象集合。
一组对象共同移位、统一色系和分别修改是不同语义。父家具与其子板件同时被选中时，应避免重复计算或重复执行。已锁定对象可以被查看或比较，但不能被批量修改顺手带走。
## 10.4 AI 请求必须绑定发送时的状态
建议每个操作请求记录 Project、房间、方案、目标对象 ID 和相关版本。用户发送后再选其他东西，不应改变已经在执行的请求目标。生成完成后应回到原任务的结果区，不能在新打开的房间突然应用。
旧建议应用前应检查它依赖的布局是否已经改变。只要无关颜色变化就阻止全部操作也会烦人；应比较与建议相关的对象和约束。必要时展示“你刚移动了桌子，要按现在的位置重新计算吗”。

# 11 商品详情与模块化家具组成
## 11.1 两个入口共用一套商品能力
你已经明确指出商品详情页有板件数量、组成和拼装展示。此前在提供的 Collections 代码中没有找到对应内容，只能说明这份代码或路径没有覆盖到，不能据此否定该功能存在。
建议将商品定义、有效配置、板件清单、附件、拼装步骤和价格规则作为共享能力。商品详情按“了解这件商品”组织；Playground 选中家具后按“调整房间里的这件”组织。两处信息一致，展示深度随任务变化。
这不需要再加一个一直占位置的全局 Assembly tab。可以从选中家具的“组成与拼装”进入临时专注状态，再返回房间。用户需要时能找到，平常不用看到全部功能。
## 11.2 放入现成家具时不要求先搭积木
用户购买现成模板时，默认看到完整家具并直接放进房间。板件拼装是理解、配置或深入 DIY 的入口，不是所有用户的必经步骤。房间家具库的默认层级应是完整家具，进入组件编辑后才展示板件库。
自由搭建与在有效模板上改配置应分开。自由搭出的概念不一定马上可制造；系统需允许创作，同时明确哪些结果已经通过规则校验，可以报价或购买。
## 11.3 拼装展示怎样一步一步做
进入拼装模式时保存原相机、选择和家具位置；场景聚焦该家具，其他房间内容弱化。用户可以查看完整组成、选一个部件高亮，或从第一步依次查看安装过程。提供上一步、下一步、播放或暂停以及自由旋转。
拆解视图中的板件位移是展示变换，退出时恢复成品状态，不能写回家具真实布局、改变购物车或生成多余零件。用户回到房间时，应仍看到原位置、原尺寸和原配置。
真实拼装步骤还需要方向、连接件、工具、先后依赖与安全可操作性。建模时先创建底板再创建顶板，不足以证明这就是实际安装顺序。必须由产品和制造验证过的步骤驱动，不应让语言模型临时编造。
## 11.4 配置变化的联动
用户换一个模块或板件后，应同步更新几何、整体尺寸、组件数量、兼容性、价格、适用的拼装步骤，以及是否仍可购买。某个颜色只改贴图、但商品配置和价格没有更新，会造成下单与所见不一致。
商品模板不应被一次用户编辑直接改写。房间里的家具实例、其他保存版本和已下单配置都需要稳定引用或独立副本，避免一个地方改动扩散到全部历史方案。

# 12 家具页面的连续探索逻辑
## 12.1 从喜欢的小东西开始
原执行文档中的 Start with what you love，允许用户从咖啡机、书、植物等生活对象进入，帮助理解一个家具怎样服务具体生活。用户选择这些偏好，不应自动把示意物品加入购物车。
Keep this Change the rest 表示保留喜欢的核心，在有效产品家族或组合规则内变化。每次变化应能说明保留了什么、新增什么、移除了什么，以及数量和价格是否变化。
## 12.2 同一件家具在不同尺度下看
A piece A corner A room 是看同一件或同一组家具的不同环境尺度。切到房间视角不能把数量变多；See the other side 是看另一面，不是生成另一件；Keep this version 应保存有效配置和所处环境，不是只存一张图。
商品变体替换、同家族配方、加配件、多件组合、已有产品改造、组件兼容和空间搭配，是内部需要区分的七类关系。用户不应因此面对七个顶层功能区。
## 12.3 组合与后续升级
两辆推车组成一个岛台时，购物清单应反映两件主体和所需连接配件，不能把一个视觉组合当成单件价格。已有家具加一块板或改结构时，只买差额必须建立在旧型号、尺寸、连接方式和所需部件真实兼容的基础上。
原型中采用同宽同高等约束，是该原型的处理方法，不能直接推广成全产品通用规则。候选组合数量、动画动作数量和原型测试通过，不等于实际销售 SKU、制造验证或端到端购买已完成。

# 13 视角和动线
## 13.1 三种看空间的方法
第三人称用于看整体位置、比例与家具关系；第一人称用于从人的高度看视线和空间感；二维平面用于处理尺寸、边界和布局。它们应对应同一个场景，不应变成三份各自保存、各自丢数据的方案。
第一人称需要容易理解的进入方式，例如在平面或场景中选择起点，再走动或沿路线观看。进入后保留明显的退出和回到整体视角入口，避免用户迷失在模型内部。
## 13.2 动线不是相机动画
用户希望看到从门口到桌边、从床到衣柜、拿东西再回来的走动路径。可以将动线作为独立叠加层，并允许选起终点、查看关键通道或播放沿路视角。开关动线不应改变家具位置。
路径绘出来和实际能通行不同。判断需考虑家具真实外轮廓、门的开启、抽屉或椅子使用空间及尺寸准确性。未测量的房间可以显示建议路线，但不能宣称已完成可靠净距或无障碍校核。
## 13.3 动线怎样连接 AI
用户说“从门口到椅子总要绕路”，Eva 应先理解目标路径和需要保留的家具，再指出具体冲突，提出一两个调整。预览应同时显示家具变化和路线改善，让用户看得出理由。
当前代码存在第一人称、巡游和航点等相关基础，不等于你要求的生活动线分析、净距检查和路径解释已经完整实现。这些要单独验收。

# 14 自动同步 手动保存 回看与复制
## 14.1 你已经明确的保存规则
每个 Project 有一个始终更新的最新自动同步工作稿；用户还可以手动保存最多十个不同想法。手动保存是固定状态，不应被后续自动同步悄悄覆盖。十个名额满了，也不应停止最新工作稿的自动保存。
保存要包含布局和家具配置，不只是截图。建议还包括门窗与尺寸、家具位置和组件、角色与锁定、与该方案相关的需求、以及必要视角和动线。图片可以作为方便找回的预览，但不能代替可恢复数据。
## 14.2 回看旧版本不消灭新版本
用户在当前工作稿 C，打开旧保存 A，应进入明确的历史查看状态。可以再看 B，也可以回到 C。单纯查看 A 不写回自动同步工作稿，不消除 C，不倒退已经下过的订单。
如果用户要从 A 继续修改，就需要形成新的工作状态，同时保护 C。可行政策包括先把 C 保存在可用手动名额，再以 A 继续；或者基于 A 复制一个 Project。具体默认方式尚未确定，不能把任何一种写成已获批准的要求。
## 14.3 十个保存名额满了怎么办
此时依然允许浏览全部保存和继续编辑最新工作稿。新建第十一个手动保存时，应让用户选择替换哪个保存、删除不需要的版本或复制 Project 后继续。不能自动淘汰最旧想法，也不能偷偷覆盖当前工作稿来腾名额。
系统内部为了防止意外而保留的恢复记录，与用户可见的十个手动保存是否分别计数，需要进一步定义。界面文案必须让用户知道自己正在覆盖一个固定保存还是更新工作稿。
## 14.4 复制 Project
复制当前工作稿和复制某个旧保存应有明确来源。复制后布局和配置可独立修改，原 Project 不变。共享的只读商品资源可以复用，但用户修改的数据不能相互串改。
聊天可以保留来源摘要或按政策复制，订单只能作为关联历史，不能复制出新的实际订单。复制后的名称、目标房间和 AI 记忆适用范围也需要更新，避免 Eva 仍把原项目的临时要求当成当前全部要求。
## 14.5 同步失败和多设备
建议显示正在保存、已同步、离线或同步失败等真正状态。页面关闭前应保留未同步改动并可恢复。现有服务端快照已有 expectedRevision 等并发控制基础，但多标签页冲突的产品体验仍需要完整设计。
冲突时不能静默用最后一次写入覆盖另一份有效工作。应保留可恢复副本，解释发生变化的 Project 和时间，再让用户继续合并或选择。历史查看、自动同步、手动保存与撤销是不同机制，不能靠同一个含糊的 Save 按钮承担。

# 15 从方案到真实购买
## 15.1 三条都需要成立的购买路径
现成商品路径是：列表 → 详情 → 有效配置 → 购物车 → 结算。房间路径是：选中家具 → 查看配置与价格 → 确认购买该件或所选多件 → 购物车。需求方案路径是：测评或对话 → 候选 → 采用具体家具 → 必要的尺寸与兼容检查 → 购买。
第二和第三条都不应要求全屋设计完成。用户只决定了推车，可以先买推车。场景中的其他概念、参考或已有家具保持原状态。
## 15.2 购买前的真实清单
清单应准确反映商品及配置版本、部件或套装、数量、所选颜色和材料、价格及交付服务。需要测量确认、询价或人工核验的条目明确标识，不能显示一个可点击的假结算按钮让用户误以为可直接交付。
购买动作与商品资料的关系应可追溯。用户在画布里看到的高度、板件数和颜色，必须与购物车相符；一组家具的总价应区分现在购买、以后考虑与已经拥有的部分。
## 15.3 购物车与画布之后的变化
用户在购物车中明确改配置，系统可以询问或清楚提供同步回房间的选择。用户在房间里临时试其他颜色时，不应悄悄修改已经放入购物车的商品。准备结算时发现二者不同，应显示具体差异而不是笼统报错。
订单完成后固定当时配置、价格与服务条件。继续探索可以基于已购买家具，但不能重新解释为尚未购买的候选。未来升级应识别已有部件和新增需求，避免重复销售已有部件或承诺未经验证的兼容性。
## 15.4 当前实现与交易风险边界
主站存在商品、购物车、结算和订单相关结构，并不代表所有配置都已接入真实 SKU、库存和付款。Playground 中可见确定性的示范价格逻辑，必须与实际商业报价区分。
发货、退款、部分交付、售后和库存不是仅靠一个生成模型就能成立的能力。当前文档与代码没有证明这些全部完成；正式交易需要对接真实规则和可验证的交付能力。
 
# 16 具体用户操作案例
本章的页面和按钮名称是用于检验操作是否连续的建议名称。每个案例同时说明用户动作、AI 责任与容易出错的位置；不是宣称这些流程已经全部上线。
## 16.1 只想买一件现成柜子
从首页商品入口进入列表，筛选尺寸，打开详情，选浅木色，直接加入购物车并结算。Eva 可以回答材质和尺寸问题，但不要求先做 quiz 或创建房间。订单保留所选配置。风险是把直接购物用户带入长测评或空白画布，造成放弃。
## 16.2 看中现成家具但想先放进房间
在商品详情选好颜色，点“放到我的房间”；当前只有一个明确房间就直接试放，有多个目标才选择。进入 Playground 后保留颜色和型号，用户拖到墙边，再查看尺寸。Eva 只补问影响适配的信息。返回详情或列表时保留来源和浏览状态。
## 16.3 从生活困扰进入
首页点“帮我理清需求”，选择玄关杂乱，补充每天出门要找包和钥匙。结果给两个具体方向；点其中一个进入当前 Project 的玄关，试放挂板和坐凳。AI 将“进门随手放”作为这次功能需求，不把一次结果固定成全局风格。可以只买坐凳。
## 16.4 已在房间中 不知道颜色怎么选
点击柜子，对 Eva 说“不知道浅木色还是白色”。聊天附近出现两种视觉选项，点选在同一柜子上连续预览。Eva 不开启完整生活方式问卷。用户采用一款后更新该家具配置；未采用的预览不写成长期偏好。
## 16.5 对测评结论不满意
结果页提示某风格，用户说“颜色可以，开放收纳不喜欢”。直接修改收纳偏好或相关答案，保留其他已回答内容。AI 解释将改为带门方案，候选随之更新。不能要求重填全卷，也不能把不喜欢的结果继续作为推荐依据。
## 16.6 同一房间重新做测评
在房间方向入口点“试另一种感觉”，做第二次视觉选择。结果保存为本房间新的探索记录，原布局不动；点“在新方案里试试”才形成替代布局。AI 能比较两次差异，但不能把最近一次自动设为全部项目的默认风格。
## 16.7 两个房间用不同风格
在 Project 中从客厅切到卧室，说“这里想更安静，别用客厅的绿色”。AI 绑定卧室，保留客厅已采用方案。用户再回客厅时仍看到绿色。全局喜好只能作为参考，不能抹平房间之间的区别。
## 16.8 给妈妈家找灵感
浏览商品时说“这个是给妈妈家看的”。如果只是记下，放入独立想法；准备布置时选择或建立妈妈家的 Project。AI 不改变用户本人家里的尺寸和审美。页面切换应显示目标项目，避免向错误房间放置商品。
## 16.9 两周后回来继续
从 Project 列表打开原项目，看到上次布局和“尺寸待确认”的短摘要。用户今天先看灯，Eva 跟随新任务，原柜子问题保留。价格或可用性已变时，在相关购买位置显示变化；不能重写旧截图或假装旧报价仍有效。
## 16.10 同时保留两个柜子方向
选中现有柜子，点“换款”，连续试开放与带门版本。用户点“保留这个想法”，保存 A，继续试 B，工作稿自动同步。比較时使用同一相机；退出比较回工作稿。候选不会作为两件重叠家具一起购买。
## 16.11 把一个方案的局部拿到另一个方案
查看 B 时选中推车，点“复制到方案 A”并确认目标。A 的布局其他部分不动，推车形成独立实例。AI 可以解释会替换还是新增，不能把整个 B 场景覆盖 A；后续在 B 改推车颜色也不改 A。
## 16.12 只是随口想以后做咖啡角
在当前工作区对 Eva 说“以后这里也许做咖啡角，先记着”。AI 留下可找回的想法，必要时标在当前区域。用户继续摆书桌。不能自动生成咖啡家具、消耗额度、弹出新项目或覆盖当前任务。
## 16.13 用网格画不规则房间
从建立房间进入轮廓编辑，画 L 形，填写两组尺寸并加门。点建立后必须保持该轮廓。AI 只能补充摆放或指出尺寸冲突，不能用面积重新猜矩形。用户能回到二维检查并修改原轮廓。
## 16.14 上传照片 还不知道精确尺寸
在房间入口上传照片，系统先明确用途是参考、近似重建还是单件识别。用户选择近似房间，识别后的家具允许逐个校正，尺寸显示估算。Eva 要一个关键长度帮助定尺度；没有测量时仍能探索，准备购买相关家具前再确认必要尺寸。
## 16.15 选中一块板让 AI 改颜色
点击柜子，再点“编辑组成”，点左侧板；画布高亮与输入目标都显示左侧板。说“换成绿色”，只修改适用的该板材质。若绿色并非可售选项，系统应说明概念预览或给有效替代，不能让界面与订单配置分离。
## 16.16 一次调整三件家具
开启多选，依次点桌、柜、推车，输入处显示三件。说“保持柜子位置，把另外两件颜色协调一下”。AI 保留对象集合和细化约束，预览实际改动。发送后用户改选灯也不改变这个请求目标。
## 16.17 看板件数量和拼装步骤
选中现成柜子，点“组成与拼装”，看到与商品详情相同的清单。点板件高亮，点“开始拼装”逐步播放；可以暂停旋转。退出回到原房间视角与家具位置。拆解动画不能让系统误以为家具被拆散或数量增加。
## 16.18 检查柜子会不会挡路
把柜子拖近门，看到相关开门或间距提示；点提示开启动线，选择从门到书桌。Eva 提出更浅柜子或小幅移位的候选。查看建议时对比路线和价格变化，用户决定后才应用。估算尺寸不能产生“保证可通行”的结论。
## 16.19 从人的视角看看
点视角入口的“走进房间”，选择门口起点，行走或沿路线观察。按返回恢复进入前的第三人称位置。行走不会改家具布局，动线可开关。卡在模型里时有重置位置，键盘、触屏和减少动态效果都应有可理解方案。
## 16.20 回看旧方案再返回最新
工作稿 C 已同步，点保存 A 进入历史预览，再点 B，最后点“回到最新工作稿”。C 的所有新调整都还在。旧版本界面有清楚状态，不出现会误写回的模糊保存按钮。AI 可以比较历史，但不把旧需求重新变成当前全局要求。
## 16.21 十个想法已满 还想从旧版继续
打开 A 后点继续编辑；系统说明需要先保护当前稿 C。可以选择替换某个手动保存来留住 C，或复制 A 到新 Project。具体默认政策待定，但不能删最旧版本，也不能为了名额停自动同步。用户取消后全部状态保持。
## 16.22 只购买方案中的一件
房间里有用户已有沙发、参考茶几、已配置的模块柜和未确定灯。只选模块柜加入购物清单，核对配置并下单。其他物体不进入订单，房间不必标为“设计完成”。下单后可继续为灯做探索。
## 16.23 多标签页和异步任务
标签页 A 在客厅生成，标签页 B 在妈妈家选家具。任务结果必须归属 A 的 Project 和方案；B 不自动跳转或被替换。用户在 A 切到卧室时，结果以可找回通知进入原任务。必要时取消或稍后应用，不能靠全站最后活跃房间来路由。
## 16.24 旧 AI 建议遇到手动修改
Eva 曾建议把桌子靠窗，用户已手动挪到另一面墙。稍后点击旧建议时，系统检查相关变更，提供重新计算或查看旧预览。不能无声覆盖新摆放。反过来，只改了无关装饰品的颜色，也不必让整套建议失效。
## 16.25 喜欢一张图但只喜欢其中一件
在灵感页收藏图片后，Eva 不推断用户接受整套房间；用户点书柜或说明只喜欢书柜，系统记录具体关联。之后推荐可参考该柜的特征，不把图片中的墙色、预算或生活方式都当成用户偏好。
## 16.26 从页面之间来回看
从 quiz 结果进入商品列表、打开详情，再放进房间，最后返回列表。每一步保留 Project 和目标，返回时恢复筛选与滚动。助手不会重新问已经回答的内容，也不会在全站到处弹出一套同样的建议。
## 16.27 购物车已经有一款 画布又试了另一款
用户把木色柜加入购物车，随后在房间试白色。只有明确更新购买配置才修改购物车。点结算时如果画布采用白色而车里是木色，显示对应差异与选择。已付款订单不随试验改变。
## 16.28 多人意见和不同预算并存
用户给自己设置预算，又代伴侣回答另一轮测评。系统保留回答来源与适用范围，不直接覆盖。AI 可以提出共同点和冲突，但不能把两个人平均成一个固定偏好。多人协作界面的具体权限仍属待设计事项。
## 16.29 生成失败或只有一部分成功
全屋任务中已有五件家具成功，两件失败。界面保留成功结果、原方案和任务记录，说明失败对象并允许局部重试。AI 不再从头生成七件造成额外成本，也不在退出页面后丢失用户输入。是否收费与重试规则应在真正涉及额度时清楚说明。
## 16.30 不同设备和输入方式
触屏用户要能多选、查看组成和退出第一人称，不依赖悬停或 Shift。键盘用户应能找到焦点、关闭临时层并返回画布；移动设备先完成查看与必要调整，复杂编辑的支持范围应明确。相机拖动和家具拖动要容易区分，避免每次查看都误移家具。

# 17 当前 Playground 的设计与具体问题
## 17.1 当前界面的组织方式
当前独立 Playground 以大面积三维或二维视口为中心，有项目入口、Tools、Properties、聊天和多种浮动卡片。Studio 中还有房间规划相关视图、上传、帮助、项目和建议等弹层。部分卡片可拖动；沉浸模式隐藏界面并保留相关树的设计也在当前代码中出现。
这个方向回应了你的顾虑：功能太多时，传统固定三栏难以安排，画布空间也会受限。问题不是“浮动一定不正式”，而是用户能否知道自己在哪、当前对象是什么、点下去有什么后果，以及怎么恢复。
今天早期提出的工作台式视觉方案被你明确否定。它不应作为已经接受的设计基础。后续方向是围绕房间里的对象与用户当前任务组织入口，同时保持少数稳定的全局位置。
## 17.2 初始对象和任务不匹配
现有新项目包含 CAD 柜体相关起点。想做房间的用户可能不知道这是示例、自己的数据，还是必须先删除的内容。建议清楚标明示例和当前任务，并提供建立房间或先挑家具的直接起点，而不是让用户自己整理工具窗口。
## 17.3 模式会改变同一句话的含义
ModeDropdown 有 Furniture、Room Layout、Interior Design，以及 Inspiration Talk、Creative Mode、Guided 两个维度。聊天分流中 Talk 强制聊天，Creative 强制生成。这可能让“帮我做柜子”只得到文字，也可能让普通问题被送入生成。
建议普通对话由当前意图决定回应与操作，必要时提供具体的生成预览动作。高级模式可保留，但不能要求普通用户先把 AI 调到正确模式，才听得懂一句自然语言。
## 17.4 画轮廓后又被转成文字
RoomGridCard 的提交会把网格描述发入聊天流程；复杂形状存在被概括成面积与外接矩形的风险，也受当前聊天路径影响。按钮写“生成这个房间”，用户就预期精确采用自己画的形状。
应让明确的几何输入直接进入房间模型；AI 负责补充和布置，不能默默重猜轮廓。操作是否成功需要有对应场景变化或明确失败，不是只出现聊天文字。
## 17.5 Catalog 的默认内容层级不对
当前 Catalog 读取横板、竖板和背板等模板。对于从零建板件的人有用，但对要挑完整模块家具的人不直觉。建议房间阶段默认完整家具，选中家具进入组成后才展示可用板件，主动自由搭建另有入口。
## 17.6 画面选择和 AI 目标没有可靠连接
场景快照包含家具和位置等上下文，但在所检查的构建函数中没有看到当前选中对象 ID 直接进入该快照合同。不能仅因为画布有高亮，就假设 AI 已知道“这个”是哪个。
应将目标 IDs、对象层级和作用范围作为明确请求数据，并在输入处显示。当前快照还有对象数量上限，复杂项目需要明确筛选与补充读取，避免用户选中的目标刚好不在上下文里。
## 17.7 浏览生成记录可能直接应用
Generations 的部分卡片点击会应用房间场景或替换单件，另有加号用于添加，也已有详情入口。问题是不同入口的含义不统一，不能笼统说完全没有预览。
用户以为点缩略图只是看看时，不应改掉当前布局。应统一查看、添加、替换各自行为，替换范围明确且可恢复，避免依靠一个小图标承载重大区别。
## 17.8 Reference 的内容会变
Reference 兼有辅助平面视图、物体图像等用途，选中对象后内容变化可能让用户误以为参考图丢了。应说明当前显示的是哪种内容；用户固定的参考不应被选择行为抢占。
## 17.9 多个列表让同一件东西难找
Catalog、Inventory、Generations、Starred、Chat history 从实现角度不同，但用户只记得“刚才那个浅木色柜子”。同一物体应有稳定身份，可从多处访问；Eva 应能协助找回。
列表操作需明确是移出房间、删除生成记录、取消收藏还是删除项目内容。一个模糊 Delete 可能让用户担心永久丢失。库中资源与场景实例的生命周期不应混在一起。
## 17.10 新对话不等于重新设计
用户点 New conversation 可能只是想试另一个方向，但新对话并不必然隔离现有房间和项目偏好。必须区分同项目新讨论、保留原方案再试一个、以及建立独立 Project。涉及清除工作时再澄清，不应每次“重新来”都自动新建整个家。
## 17.11 保存和价格容易造成错误预期
关闭 Properties 只是关闭属性界面，不能被当成保存动作。用户需要看见真实同步状态、固定保存和当前工作稿。Inventory 的模拟价格也不应像真实报价一样引导购买。
当前已存在项目持久化及服务端快照 revision 基础，不能说完全没有保存；但本次未验证你要求的十个手动保存、无损历史预览、完整复制与购买配置冻结已经全部实现。

# 18 主站与独立工作区的技术现状
## 18.1 已存在的基础能力
独立工作区的 README 和代码显示 Next.js、React、React Three Fiber、Three.js、Zustand 等基础。API 包括聊天、房间生成、单件生成、布局安排、解释与建议；房间生成可以通过流式事件呈现进度和对象结果。
本地项目接口使用本地 JSON 文件和客户端持久化路径，部分对话能力可选用 Supabase。缺少相关 API 密钥时，页面可以加载，但对应生成接口会返回不可用；“界面能打开”不是“AI 端到端能工作”的证明。
当前 package.json 声明的部分版本为 Next 16.3.1、React ^19.2.8、Three ^0.185.0、R3F ^9.7.0、drei ^10.7.8、Zustand ^5.0.1，并要求 Node 至少 24。这里记录的是项目声明，不是对最新发布版、安装结果或兼容性完成验证的结论。
## 18.2 生成流程与真实配置之间的距离
已有房间生成方向包含结构化尺寸与家具清单、风格信息、边界和碰撞等验证，以及图像到网格的生成和替换。某些布局使用户型预设。这些能帮助快速形成场景，但不能自动导出可制造的模块配置。
CAD 中已有由底板、中板、顶板、侧板和背板组成的参数化柜体基础。其默认厚度等是代码和研究设置，不应直接升级为生产规格。AI 网格与 CAD 板件当前是不同能力线，需要明确何时可转换、何时只能视觉参考。
## 18.3 数据和工作流仍有分界
Prisma 中 CanvasPlaygroundProject 与其他 Project 概念存在独立结构，Canvas 对话与账号其他聊天也分开。主站 Room Plan 更接近家具采购计划及 needed、considering、decided、purchased 等状态，不等于空间墙体和家具坐标布局。
Design Brief 用于汇总偏好、Room Plan 和设计需求，与图像生成衔接；不能仅根据名称就认定已经与 Playground 的完整场景数据打通。Project 记忆和聊天工作流的相关功能开关也不能忽略。
## 18.4 最需要建立的共同合同
建议统一可引用的 Project、房间、方案和家具实例身份，明确测评结果、AI 请求、空间快照、商品配置与购买清单如何关联。场景采用具体配置版本，订单再固定购买版本；不同页面不重新推导一套不一致的数据。
每次 AI 操作记录输入范围、依赖状态、输出对象、执行状态和可恢复结果。家具配置记录几何、BOM、价格规则与兼容验证版本。图片、网格和渲染可作为派生资产；不能反过来把图片当成全部真实状态。
## 18.5 本次没有做的验证
本次是文档归纳和静态代码核对，没有修改应用，也没有重新运行支付、真实订单、供应商生成和完整用户端到端测试。代码里存在某路径，不证明所有环境已启用；原文档中的测试数字也不作为今天的最新测试结果。

# 19 开放画布怎样减少繁琐
## 19.1 稳定入口和情境操作共存
建议保留开放房间画布，同时让 Project 身份、当前房间或方案、保存状态、视角、添加家具和购买入口稳定。常用的选中对象操作直接出现在对象附近或固定情境区域；深层参数按需要展开。
不必把每项功能都分成一个可以随意漂移的浮窗，也不必退回始终占满的三栏。浮动适合短暂、靠近目标的操作；稳定区域适合项目状态和连续浏览。正式感来自一致、可预测和可恢复的行为，而不是面板边框数量。
## 19.2 一次围绕一个当前任务展开
浏览商品时出现连续家具浏览区；点换款后同一区域变成替换候选；进入组成后转为该家具的模块和板件。用户不需要开三份目录、三个窗口，再手动关掉两份。
Eva 默认可以收成短输入区，展开讨论时才显示完整对话。聊天不能长期遮住正在修改的柜子或地面。对象目标在收起与展开之间应保持，而不是每次打开重新解释。
## 19.3 普通动作连续 高影响动作可检查
换色、移动和旋转即时反馈并支持撤销；连续换款使用一轮试换；AI 重排整个房间先预览；查看旧保存是历史浏览。将所有操作统一变成“预览、应用、确认、保存”四步，会产生不必要负担。
每个入口还应有明确的退出与返回：退出板件回到整件，退出拼装回到房间，退出第一人称回到原视角，退出历史回到工作稿。多个临时层不能让一个 Back 按钮随机返回网站首页。
## 19.4 推荐控件位置仍是可测试方案
曾讨论过底部可收起家具浏览区、少量固定工具和情境操作。这些是可能的布局方向，不是你的最终选定设计。后续应先用“换柜子、改一块板、保留两种想法、只买一件”验证交互，再决定面板具体位置和视觉样式。
你否定的早期设计，以及后来发现过度分模块、过度确认的问题，应被保留为修正依据。不能把被否定方案换几个颜色又当作已经认可的方案继续推进。
