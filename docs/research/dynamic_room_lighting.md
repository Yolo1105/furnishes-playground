## 1. Real-time GI in three.js r185/r186: SSGI, SSR, GTAO, LightProbeGrid

### Takeaway
As of r186 (2026-09-24) three.js ships two usable real-time indirect-light tools: the screen-space `SSGINode` (WebGPURenderer/TSL, needs TRAA, has classic screen-space leaks and noise) and `LightProbeGrid` (an L2-SH irradiance volume baked on the client GPU in seconds, incrementally, now on both WebGPU and WebGL). Neither has published ms/frame or fidelity numbers against baked lightmaps; the probe grid is the more robust fit for edited rooms but gives low-frequency diffuse GI only and still has unresolved light leaking.

**SSGINode (screen-space GI + AO)**
- It is an addon imported from `three/addons/tsl/display/SSGINode.js`; constructor takes beauty, depth and normal texture nodes plus the camera; it outputs separate AO (`getAONode()`) and GI (`getGINode()`) textures — [SSGINode docs](https://threejs.org/docs/pages/SSGINode.html)
- Defaults: `sliceCount` 1 (range 1–4), `stepCount` 12 (1–32), `radius` 12 (1–25, world space), `thickness` 1, `aoIntensity` 1, `giIntensity` 10, `expFactor` 2, `backfaceLighting` 0, `useTemporalFiltering` true, `useScreenSpaceSampling` true — [SSGINode docs](https://threejs.org/docs/pages/SSGINode.html)
- Cost model stated in docs: total samples per pixel = `sliceCount × stepCount × 2`; both parameters are described as having a "big performance cost" and to be "kept as low as possible" — [SSGINode docs](https://threejs.org/docs/pages/SSGINode.html)
- Presets with temporal filtering (recommended): Low 1×12, Medium 2×8, High 3×16; without temporal filtering: Low 2×6, Medium 3×8, High 4×12 — [SSGINode docs](https://threejs.org/docs/pages/SSGINode.html)
- Documented artefacts: temporal filtering requires `TRAANode` and "introduces typical TAA artifacts like ghosting and temporal instabilities"; "AO and GI can only have influence within that radius"; the thickness heuristic "allows light to pass behind surfaces past that thickness value" — [SSGINode source, dev branch](https://raw.githubusercontent.com/mrdoob/three.js/dev/examples/jsm/tsl/display/SSGINode.js)
- Render targets: AO is `RedFormat`/`UnsignedByteType`; GI is `RGBFormat`/`UnsignedInt101111Type` (the RG11B10 change) — [SSGINode source, dev branch](https://raw.githubusercontent.com/mrdoob/three.js/dev/examples/jsm/tsl/display/SSGINode.js)
- References the implementation follows: SSRT3 / "SSAO with visibility bitmask" (SSILVB) by cdrinmatane — [SSGINode docs](https://threejs.org/docs/pages/SSGINode.html)
- The official example `webgpu_postprocessing_ssgi` (r186 tag) is a Cornell-box scene (red/green walls, two boxes, one point light at intensity 100, near-black ambient `#0c0c0c`), uses MRT (`output`, `diffuseColor`, packed `normal`, `velocity`), `ssgi` + `traa`, with `sliceCount = 2`, `stepCount = 8`. Composite: `scenePassColor.rgb * ao + scenePassDiffuse.rgb * gi.rgb` — [example source r186](https://raw.githubusercontent.com/mrdoob/three.js/r186/examples/webgpu_postprocessing_ssgi.html); [live example](https://threejs.org/examples/webgpu_postprocessing_ssgi.html)
- The example deliberately leaves device pixel ratio off: `//renderer.setPixelRatio( window.devicePixelRatio ); // probably too costly for most hardware` — [example source r186](https://raw.githubusercontent.com/mrdoob/three.js/r186/examples/webgpu_postprocessing_ssgi.html)
- PR #31890 (zalo, merged 2025-09-12, milestone r181) improved temporal jitter; the author noted "there is a persistent screen-space noise pattern that overlays everything" in the earlier version — [three.js PR #31890](https://github.com/mrdoob/three.js/pull/31890)
- A search-result summary claimed r186 SSGI gained "SVGF denoising, blue noise sampling and resolutionScale"; I could not confirm it: the dev-branch `SSGINode.js` contains no `resolutionScale`, SVGF or blue-noise code, and the r186 release notes do not mention them — [SSGINode source, dev branch](https://raw.githubusercontent.com/mrdoob/three.js/dev/examples/jsm/tsl/display/SSGINode.js); [r186 release page](https://github.com/mrdoob/three.js/releases/tag/r186)

**LightProbeGrid (irradiance probe volume)**
- Definition: "A 3D grid of L2 Spherical Harmonic irradiance probes that provides position-dependent diffuse global illumination. The grid is a Light, so adding it to the scene applies its baked irradiance to every lit node material automatically." Data lives in one RGBA `RenderTarget3D` atlas packing nine L2 coefficients into seven sub-volumes; "Baking is fully GPU-resident: cubemap rendering, SH projection, and texture packing all happen on the GPU with zero CPU readback." — [LightProbeGrid docs](https://threejs.org/docs/pages/LightProbeGrid.html)
- API (r186): `new LightProbeGrid(width, height, depth, widthProbes, heightProbes, depthProbes)`; probe-count defaults are `Math.max(2, Math.round(size) + 1)` per axis (about one probe per world unit); `falloff` fades contribution outside the volume. Import `three/addons/lighting/LightProbeGrid.js` for WebGPURenderer, `LightProbeGridWebGL.js` for WebGLRenderer — [LightProbeGrid docs](https://threejs.org/docs/pages/LightProbeGrid.html)
- `bake(renderer, scene, options)` renders a cubemap at each probe and projects to L2 SH. Option defaults: `cubemapSize` 8, `near` 0.1, `far` 100, `bounces` 0, `sampleCount` 512, `start` 0, `count` (remaining), `pass` 0 (0 = direct light; later passes sample the previous pass). Shadow-casting `SunLight` instances are temporarily replaced by equivalent directional lights during bake — [LightProbeGrid docs](https://threejs.org/docs/pages/LightProbeGrid.html)
- Runtime shading cost: per-fragment texture samples rose from 3 to 7 when the design moved from L1 to L2; memory is about 24 KB for a 6×6×6 grid and "negligible even at 12×12×12 scale"; bake time is "dominated by cubemap rendering" — [three.js PR #33125](https://github.com/mrdoob/three.js/pull/33125)
- Known weakness acknowledged in the PR discussion: unresolved light leaking, and L2 SH cannot represent highly localized bright features such as windows or sun patches — [three.js PR #33125](https://github.com/mrdoob/three.js/pull/33125)
- Incremental baking (PR #34486, opened 2026-09-06, merged 2026-09-07, r186): previously baking a large grid blocked rendering; `start`/`count`/`pass` let "applications ... capture a few probes per frame and display their results immediately"; "Each indirect pass samples a snapshot of the completed previous pass"; validated on WebGPU Sponza with "490 probes, both bake passes, cascaded shadows, GI visibility, lighting changes, and restarting" — [three.js PR #34486](https://github.com/mrdoob/three.js/pull/34486)
- Official example `webgpu_lightprobes_sponza` (r186): 21×11×9 unit volume with 10×7×7 probes, `cubemapSize: 32`, `near: 0.05`, at most 4 probes per frame (`Math.min(4, totalProbes - bakeIndex)`), 0–2 bounce passes, lit by a `SunLight`; any change to light position, intensity, shadows or bounce count calls `resetProbeBake()` — [example source r186](https://raw.githubusercontent.com/mrdoob/three.js/r186/examples/webgpu_lightprobes_sponza.html)
- WebGPU support is new: on 2026-04-20 a maintainer wrote "WebGPURenderer does not yet support this class. It is still experimental and we add a version for WebGPURenderer in one or two releases" — delivered in r186 — [discourse: light probes WebGL vs WebGPU](https://discourse.threejs.org/t/how-to-create-a-comparable-light-probes-webgl-vs-webgpu/91098)
- A third-party project plan built on r186 (tile-map viewer, not archviz) describes a production-style schedule: debounce about 500 ms after scene changes, bake 4–8 probes per frame at 8–16 px cube faces, about 576 probes for a 48×36 map ("at 8 per frame about 72 converge frames per pass"), memory "under 1 MB", crossfade intensity over about 600 ms, and enable the grid only on High/Ultra tiers (none on Low/Medium). These are design targets in an issue, not measurements — [thirdfold issue #235](https://github.com/tougenrip/thirdfold/issues/235)
- Practitioner advice on probe volumes (Usnul, 2026-05-06/07): L1 roughly halves cost for diffuse-only; "check if your probe is trapped just behind a surface...push it out, preferably forward a bit. This alone fixed majority of nasty artifacts." — [discourse: Global Illumination](https://discourse.threejs.org/t/global-illumination/91243)
- An e-commerce 3D viewer project (shopware/dive) opened a spike on 2026-09-21 pointing at the Sponza probe example; no findings posted yet — [shopware/dive issue #249](https://github.com/shopware/dive/issues/249)

### Inferences
- SSGI example cost: at the example's 2×8 setting the docs formula gives 2 × 8 × 2 = 32 depth/colour taps per pixel per frame, plus the MRT pass (4 attachments) and TRAA. This is why the example disables device pixel ratio. On phone GPUs at DPR 2–3 this is unlikely to hold 60 fps without resolution scaling (estimate; no published measurement found).
- LightProbeGrid bake time for a room (estimate, from example parameters): the Sponza example bakes 490 probes at 4 per frame, about 123 frames per pass; with 2 bounces (3 passes) about 368 frames, which is roughly 6 s at 60 fps if the frame rate holds. A 5 × 4 × 2.7 m room at default density is 6 × 4 × 5 = 120 probes, about 30 frames per pass, so roughly 0.5 s per pass and 1.5 s for direct + 2 bounces at 60 fps. During the bake each probe costs 6 extra scene renders (24 per frame at 4 probes/frame), so frame time will rise while converging.
- Quality ceiling: an L2 SH grid at about 1 m spacing delivers smooth colour bleed and room-to-room brightness differences but not contact-scale indirect shadowing or sharp sun-bounce gradients that a 1–2K lightmap captures. Pairing the probe grid with GTAO (for contact occlusion) is the natural real-time stack; SSGI adds near-field colour bleed at higher cost and with leaks.
- For dynamically edited rooms, LightProbeGrid's re-bake-on-change model (seconds, in the client, no UVs needed) matches the edit loop far better than any lightmap pipeline; the trade-off is fidelity.
- Thin interior walls plus probes on a regular grid are the classic leak case (probe on the far side of a wall lighting the near side). A generated-room pipeline knows wall positions, so it can place one grid per room (the API supports multiple volumes with `falloff`) rather than one grid for the apartment.

### Gaps
- No published ms/frame or fps figures for `SSGINode`, `SSRNode`, `GTAONode` or `LightProbeGrid` on named desktop or mobile GPUs were found (three.js docs, PRs, forum and blogs all omit them). This must be measured in-house.
- No screenshots-with-metrics comparison of SSGI or LightProbeGrid against a baked lightmap for an interior was found.
- I did not verify which exact release first shipped `SSGINode` (it existed by r181, September 2025, per PR #31890).
- Mobile WebGPU coverage in October 2026 was not verified from a primary source; a search-result headline ("WebGPU Just Hit Baseline in Every Major Browser", vr.org) suggests broad support but I did not read it.
- Whether `LightProbeGrid` has any built-in leak mitigation (visibility/Chebyshev, normal bias) in r186 is unclear; PR #34486 mentions "GI visibility" in its test list but the docs describe no such option.

## 2. Server-side automated lightmap baking (headless Blender Cycles and how products do it)

### Takeaway
Fully automated "upload model, get baked WebGL scene" pipelines exist commercially (Shapespark's cloud API, built on a Cycles-based baker with automatic UV unwrapping), while consumer room planners (Coohom, Planner 5D, Homestyler) mostly offer cloud-rendered stills in minutes rather than baked lightmaps for the live view. Cloud GPU cost is small (about $0.34–$1.10 per GPU-hour for 4090/L4/A10-class in 2026); the unresolved number is bake latency per room, for which I found no published Cycles-on-cloud-GPU measurement, only Shapespark figures in the minutes range.

### Cited Findings

**How products automate it**
- Shapespark cloud API "automates creation of WebGL 3D visualizations with realistic, baked lighting": accepts FBX/COLLADA/OBJ/glTF, three calls (`POST .../import-upload-init` → `PUT` zip to a signed Google Storage URL → `POST .../import-upload-done`), with an `extras.json` whose `bake` quality is one of `"draft"`, `"low"`, `"medium"`, `"high"`, `"super"` ("Each setting corresponds to different lightmap baking parameters (the number of samples, bounces and the maximum number of lightmaps)"). Access is by request to team@shapespark.com; no bake-duration, queue or webhook details are documented — [shapespark/api](https://github.com/shapespark/api)
- Shapespark materials accept `opacityForBaking` (0–1); 0 disables the lightmap for objects with that material — [shapespark/api](https://github.com/shapespark/api) (snippet only for this field)
- Shapespark's baker is Cycles-based: 2.9.0 (2023-09-18) "Upgrade Cycles rendering engine to version 3.5: Almost 2 times faster baking & previews on CUDA & CPU devices" and "Added support for OptiX device, available on Nvidia RTX GPUs, which is about 3 times faster on average than CUDA"; 3.4.0 (2025-06-04) "Ported lightmap baking engine to Cycles 4.4 with improved CPU baking performance" and added light-tree sampling; 3.2.0 (2024-07-24) added a real-time "Bake Preview" mode; 3.6.0 (2026-02-02) HDR sky as bake light source and "Improved draft baking performance on larger scenes" — [Shapespark changelog](https://www.shapespark.com/changelog)
- Shapespark describes its engine as having "automatic UV unwrapping" so presentation needs no powerful computer — [SketchUp Extension Warehouse listing](https://extensions.sketchup.com/extension/1781a31c-8c5f-425d-a7c3-44c896e00d28/0) (snippet only)
- Shapespark guidance: "Around 100 samples should work for a draft bake and 400-800 for high quality baking", bake time roughly linear in samples — [Shapespark help: Bake](https://help.shapespark.com/hc/en-us/articles/360009198617-Bake-Lightmap-baking) (snippet only; page returned 403 to direct fetch)
- Coohom/Kujiale: design and rendering both run in the cloud; its "Cloud-Based Real-Time Lighting Rendering" (announced at the 2023 COOL+ summit, article January 2024) runs on "KooEngine" over "Coohom's global network of high-performance GPU computing clusters" and "reduces whole-house design rendering time from 2 hours to under 15 minutes", "nearly tenfold" efficiency. The article does not say whether the live view uses lightmaps, streaming or path tracing — [Coohom blog](https://blog.coohom.com/cloud-based-real-time-rendering-launched-by-coohom-boosting-rendering-efficiency-by-tenfold/)
- Planner 5D renders on its own cloud service; a rendering update cut HD renders to "30min–90min instead of 1-4h" (older blog), and current support pages list about 1–2 minutes for draft and 2–15 minutes for HD renders — [Planner 5D blog: rendering improvements](https://planner5d.com/blog/cZTe/rendering-improvements); [Planner 5D support: render processing time](https://support.planner5d.com/en/articles/5885903-renders-processing-time-web) (both snippet only; support page returned 404 to direct fetch)
- Homestyler markets cloud rendering with "photo-realistic effects in 3 minutes" and 4K output — [Homestyler](https://www.homestyler.com/) (snippet only)
- An open-source AI house generator (damhau/housegen) opened an issue on 2026-09-26 proposing exactly this architecture: second UV set via "Blender's Lightmap Pack or xatlas", "Bake per version on the GPU render service; store the lightmaps next to the version", runtime applies `material.lightMap` and "turns the real-time fill lights off where a lightmap covers the surface", aiming for "roughly 70–80% of an offline render at interactive frame rates". Open problems it lists: bake time per version and when to bake, atlas download size, and stale bakes after edits requiring fallback to real-time lighting. No measurements — [damhau/housegen issue #42](https://github.com/damhau/housegen/issues/42)

**Bake-time evidence (all that was found)**
- Shapespark staff, February 2019: a "quite small" scene at 800 samples "bakes in about 20 minutes on our desktop GPU, and about 2h on CPU"; a user's mobile Quadro M2200 took 90–450 minutes for the same scene (thermal throttling suspected). - Shapespark tutorial: a 100-sample draft bake "might take from a few to about 15 minutes" depending on model and machine — [Shapespark help: Bake your scene](https://help.shapespark.com/hc/en-us/articles/360009032738--3-Bake-your-scene) (snippet only)
- Later speed-ups to those 2019 numbers: about 2× (Cycles 3.5, CUDA/CPU) and about 3× more from OptiX on RTX — [Shapespark forum: 2.9.0 beta](https://forum.shapespark.com/t/beta-release-2-9-0-with-faster-baking-on-gpu/4637)
- Cycles camera-render reference on serverless GPU: Modal's official Blender example (bpy 4.5.0, L40S, CUDA) reports "about six seconds" per 1080p frame on GPU versus "about one minute" on CPU, and "GPUs render >10x faster than CPUs" — [Modal docs: Blender example](https://modal.com/docs/examples/blender_video)

**Running Blender headless**
- Modal's example builds the image with `modal.Image.debian_slim(python_version="3.11")`, `apt_install("xorg", "libxkbcommon0")`, `uv_pip_install("bpy==4.5.0")`, and enables GPU with `compute_device_type = "CUDA"` and `scene.cycles.device = "GPU"`; it fans out to 10 GPU containers — [Modal docs: Blender example](https://modal.com/docs/examples/blender_video)

**UV unwrapping and denoising options**
- Blender manual: Smart UV Project "cuts a mesh based on an angle threshold" and suits "mechanical objects or architecture"; Lightmap Pack "takes each of a mesh's faces, or selected faces, and packs them into the UV bounds" with pack-quality and margin options — [Blender 4.3 manual: UV operators](https://docs.blender.org/manual/en/4.3/modeling/meshes/editing/uv.html) (snippet only)
- xatlas is "a small C++11 library with no external dependencies that generates unique texture coordinates suitable for baking lightmaps or texture painting", a fork of thekla_atlas (The Witness) — [jpcy/xatlas](https://github.com/jpcy/xatlas) (snippet only)
- Trade-off reported by practitioners: xatlas "gives acceptable results, definitely better than any other form of automatic unwrapping" for lightmaps but "fails on many models" with messy imported geometry where Smart UV still works; The_Lightmapper notes xatlas can be "notoriously slower" than the default unwrapper — [Blender Artists: blender-xatlas](https://blenderartists.org/t/blender-xatlas-v0-0-6-lightmap-unwrapping-and-packing/1239767); [Naxela/The_Lightmapper](https://github.com/Naxela/The_Lightmapper) (snippets only)
- The_Lightmapper (Blender addon) automates Cycles lightmap baking with automatic material and UV setup, 32-bit HDR lightmaps, and OIDN (CPU) or OptiX (GPU) denoising — a reference implementation for a scripted pipeline — [Naxela/The_Lightmapper](https://github.com/Naxela/The_Lightmapper) (snippet only)
- A render-farm guide states OIDN is "the default and recommended choice in Blender 4.x" and that 256–1024 samples with denoising are typical for production camera renders — [SuperRenders guide](https://superrendersfarm.com/article/blender-render-settings-optimization-guide) (snippet only; secondary source)
- A small open script batch-bakes Cycles lightmaps for three.js (auto UVs, one-click baked/real-time toggle); the author (2025-05-09) reports "crazy bigger fps on mobile" after switching from real-time lights to lightmaps but gives no figures — [discourse: batch lightmap script](https://discourse.threejs.org/t/made-a-blender-script-for-batch-baking-lightmaps-to-optimize-models-for-threejs/82346)

### Inferences
- Hourly-equivalent Modal prices (my arithmetic from per-second rates): T4 about $0.59/h, L4 about $0.80/h, A10 about $1.10/h, L40S about $1.95/h.
- Per-bake cost is negligible relative to latency (estimate): a 60 s bake on a Modal L4 costs about $0.013 of GPU time; a 5-minute bake on a RunPod secure 4090 about $0.06; even 20 minutes on AWS g5.xlarge is about $0.34. At 10,000 bakes/month and 60 s each on L4 that is roughly $130/month plus CPU/memory. Cost will not decide this; turnaround and pipeline robustness will.
- Per-room bake latency (estimate, not measured): a single generated room with one 1–2K lightmap atlas (1–4 million texels, comparable to a 1080p–2K frame) at 64–256 samples plus OIDN should take on the order of tens of seconds to a few minutes of Cycles time on L4/A10G/4090-class GPUs, extrapolating from Modal's 6 s per 1080p frame on L40S and Salad's about 12 s per benchmark frame on a 4090. Add Blender start-up, glTF import, UV unwrap/pack and container cold start (image pull plus GPU attach), which can dominate for short jobs. Shapespark's own published figures (a few to 15 minutes for a 100-sample draft; about 20 minutes at 800 samples on a 2019 desktop GPU, before 2× and OptiX 3× speed-ups) indicate "minutes, not seconds" for whole-scene quality bakes. A T4 is likely several times slower than a 4090; I have no sourced T4/L4/A10G Cycles score.
- Because edits invalidate bakes, a server bake only fits an "edit in real-time preview, then bake when the layout settles" flow, with a real-time fallback while the bake is stale (the same conclusion as the housegen proposal).
- For AI-generated rooms the geometry is clean and parametric (boxes for walls/floor/ceiling), so lightmap UVs for the shell can be generated analytically (one rectangle per wall face) without xatlas or Smart UV; automatic unwrapping is only needed for furniture meshes, and those can be pre-unwrapped once per catalogue asset.
- Baking only the room shell (walls, floor, ceiling) with furniture as occluders keeps atlas size and bake time small and sidesteps per-furniture UV problems.

### Gaps
- No published measurement of Blender Cycles lightmap bake time for a single room on T4, L4, A10G or RTX 4090 was found. The numbers above are extrapolations and must be benchmarked.
- No technical description of Matterport-style or Coohom/Kujiale live-view lighting pipelines (whether they bake lightmaps, stream pixels or path-trace) was found; one Quora answer speculating about Coohom's stack was judged unreliable and not used.
- Planner 5D and Homestyler figures are from marketing/support snippets, and refer to still-image cloud renders, not lightmaps.
- Cold-start times for Blender GPU containers on Modal/RunPod serverless were not found.
- AWS Batch-specific Blender guidance was not found; AWS's documented path is Deadline Cloud.
- Shapespark API bake durations, queueing and pricing are not public.

## 3. In-browser GPU lightmap baking

### Takeaway
In-browser baking is technically feasible in October 2026 but immature: the only WebGPU/TSL baker targeting r186 (Hoodgail/three-gpu-baker v1.0.0) is about three weeks old with 2 stars and 6 commits, and the WebGL alternatives are either unmaintained prototypes or pinned to r185 and WebGL-only. None publishes bake times.

### Cited Findings

**Hoodgail/three-gpu-baker (v1.0.0)**
- Repository created 2026-09-13, last push 2026-09-17, 2 stars, 0 forks, 0 open issues, MIT — [GitHub API: Hoodgail/three-gpu-baker](https://api.github.com/repos/Hoodgail/three-gpu-baker)
- "Progressive diffuse lightmap baking for Three.js, built with TypeScript, TSL, and WebGPU"; version 1.0.0 supports three.js r186; 6 commits on main; Node 22.12+ or 24 — [Hoodgail/three-gpu-baker](https://github.com/Hoodgail/three-gpu-baker)
- Features: multi-bounce diffuse transport with next-event estimation and multiple importance sampling; point, spot, directional, rect-area and emissive lights; separate output channels (direct, indirect, ambient occlusion, albedo, normal, position, coverage, sample counts); SH9 probe grids convertible to three.js `LightProbe`; chart-aware à-trous/bilateral denoising plus an offline native OptiX worker; lossless HDR sidecar export via `LightmapIO().encode(result)` — [Hoodgail/three-gpu-baker](https://github.com/Hoodgail/three-gpu-baker)
- UVs: planar or optional xatlas shared atlases with density and padding control; `uvMode: 'generate'` replaces overlapping layouts; requirement that "UV coordinates must form one shared, non-overlapping atlas across every mesh" — [Hoodgail/three-gpu-baker](https://github.com/Hoodgail/three-gpu-baker); generate/preserve/repack modes, fixed texel density and diagnostics were added in [PR #1](https://github.com/Hoodgail/three-gpu-baker/pull/1)
- Backend: WebGPU via TSL is primary; "A CPU reference backend is available for machines without WebGPU" — [Hoodgail/three-gpu-baker](https://github.com/Hoodgail/three-gpu-baker)
- API shape: `new LightmapBaker({ backend: 'tsl', width: 256, height: 256, samples: 128, bounces: 3 })`, `await baker.prepare(scene)`, `await baker.bake({ onProgress })` — [Hoodgail/three-gpu-baker](https://github.com/Hoodgail/three-gpu-baker)
- Stated scope limits: "This is an opaque diffuse baker. Specular/refraction transport, alpha cutouts, normal mapping, HDR environment importance sampling, and animated geometry are outside v1 scope." and "Unsupported Three.js material features are rejected explicitly." — [Hoodgail/three-gpu-baker](https://github.com/Hoodgail/three-gpu-baker)
- No bake-time benchmarks or recommended sample counts are published — [Hoodgail/three-gpu-baker](https://github.com/Hoodgail/three-gpu-baker)

**lucas-jones/three-lightmap-baker**
- 159 stars, 12 commits; built on xatlas-three (UV2 unwrap), three-mesh-bvh (GPU raycasting) and three-gpu-pathtracer logic; renders world position and normal into UV2 space then casts rays per texel — [lucas-jones/three-lightmap-baker](https://github.com/lucas-jones/three-lightmap-baker)
- Self-declared TODO/limits: "High casts can cause the WebGL context to timeout"; multiple lights and light types not supported; bounce lighting not implemented; NPM package, OptiX denoise and light probes only planned — [lucas-jones/three-lightmap-baker](https://github.com/lucas-jones/three-lightmap-baker)

**Ibrahim-3d/three-lightmap-baker**
- 6 stars, 343 commits, MIT; "path-traced GI, automatic UVs, BVH ray tracing, AO and denoising"; requires three `>=0.185.1 <0.186.0`; `THREE.WebGLRenderer` with WebGL 2 + `EXT_color_buffer_float` only; `THREE.WebGPURenderer` is "not supported" (including its WebGL fallback); headless/Node baking not supported — [Ibrahim-3d/three-lightmap-baker](https://github.com/Ibrahim-3d/three-lightmap-baker)
- "WebGPU, cloud/headless execution, and the next-generation baking backend are not developed in this repository."; "This package is intentionally WebGL-only" — [Ibrahim-3d README](https://raw.githubusercontent.com/Ibrahim-3d/three-lightmap-baker/master/README.md)
- Material limits: only `MeshStandardMaterial`/`MeshPhysicalMaterial`; "Normal maps, roughness/metalness maps, `emissiveMap`, transparency/transmission, vertex colors, and custom shaders are not fully transported" — [Ibrahim-3d README](https://raw.githubusercontent.com/Ibrahim-3d/three-lightmap-baker/master/README.md)
- A search-result summary of this repo describes a recommended chain "path-traced static lightmap bake → mount completed lightmaps → isolate the baked static scene → Three.js LightProbeGrid capture → GPU L2 spherical harmonics → dynamic standard-material objects"; I could not find that text in the README I fetched, so treat as unverified — [Ibrahim-3d/three-lightmap-baker](https://github.com/Ibrahim-3d/three-lightmap-baker)

**pmndrs/react-three-lightmap**
- 156 stars, 193 commits; in-browser lightmap and AO-map baker for react-three-fiber; rendering happens "on a separate hidden canvas and WebGL context"; wishlist (not implemented) includes denoising, multi-layer lightmaps, light probes for dynamic meshes, bake-only lights, and saving/loading lightmap textures — [pmndrs/react-three-lightmap](https://github.com/pmndrs/react-three-lightmap)
- Method (author's write-up, 2020): each texel is computed by "rendering the scene into a very low-res half-cubemap and then averaging the cubemap data into the final single texel value"; "Each pass effectively adds on a photon bounce". Auto-UV finds coplanar islands and packs bounding boxes with Potpack, "far from being the most space-efficient ... but works well enough for typical small in-browser WebGL scenes". The author frames results as "good enough for a draft sketch in code" — [unframework.com write-up](https://unframework.com/portfolio/simple-global-illumination-lightmap-baker-for-threejs/)

### Inferences
- Maturity ranking for a production dependency in October 2026: none is production-proven. three-gpu-baker has the right architecture (WebGPU, r186, separate irradiance/AO channels, SH9 probes, xatlas) but effectively zero adoption; Ibrahim-3d's is the most actively developed (343 commits) but locked to WebGLRenderer and r185, so it cannot share a renderer with an r186 WebGPU viewer; lucas-jones's lacks bounce light, which defeats the purpose for indirect lighting; react-three-lightmap's hemicube method is slow per texel and draft-quality by its author's own description.
- In-browser baking moves GPU cost to the user and removes server latency and cost, but bake time then depends on the user's device; on phones and integrated GPUs a path-traced 1K atlas at 128 samples × 3 bounces may take long enough to need a progressive preview (estimate; no published timings).
- A pragmatic use of an in-browser baker is as a progressive refinement on capable desktops (bake shell lightmap in the background, crossfade in), with LightProbeGrid + AO as the universal baseline.

### Gaps
- No bake-time numbers for a simple room were published by any of the four projects; this needs an in-house test (suggested: 5 × 4 × 2.7 m room, 512² and 1024² atlas, 64/128/256 samples, 3 bounces, on an M-series laptop, a mid-range discrete GPU and a recent phone).
- WebGPU requirement specifics (required features/limits, compute vs render-pipeline use) for three-gpu-baker were not documented in what I could read.
- Last-commit dates for lucas-jones, Ibrahim-3d and pmndrs repos were not retrievable from the pages fetched; maintenance status is inferred from commit counts and stated scope.
- Robustness of three-gpu-baker on real furniture assets (it rejects unsupported material features) is unknown.

## 4. Hybrid patterns (baked shell + dynamic furniture, recolourable lightmaps, contact shadows, reflection probes)

### Takeaway
Shipping archviz products use a hybrid: baked diffuse lightmaps for static geometry, reflection probes (about one per room) for specular, and real-time material swaps on top; the same pattern maps onto three.js r186 as shell lightmap + `LightProbeGrid` for movable furniture + cheap contact/accumulated shadows. Evidence for specific three.js implementations of recolourable lightmaps and box-projected reflections is thin.

### Cited Findings
- Shapespark (baked-lightmap WebGL product): "You need light probes to get reflections"; "Each room should have one. Sometimes it makes sense to use one light probe for larger areas"; the editor auto-places probes via room detection, which "doesn't always succeed" — [Shapespark forum: light probes](https://forum.shapespark.com/t/when-how-to-use-light-probes/99)
- Shapespark 3.6.1 (2026-05-18): "Automatically update reflection probes when objects or materials are switched." — [Shapespark changelog](https://www.shapespark.com/changelog)
- Shapespark's Material Picker extension lets viewers change object materials in real time on a baked scene (each option can replace multiple materials) — [Shapespark help: Material picker](https://help.shapespark.com/hc/en-us/articles/7236261428893-How-to-set-up-Material-picker-extension) (snippet only)
- three-gpu-baker emits direct, indirect, AO and albedo as independent channels and SH9 probe grids convertible to three.js `LightProbe`, i.e. the ingredients for irradiance-only (albedo-free) lightmaps plus probe-lit dynamic objects — [Hoodgail/three-gpu-baker](https://github.com/Hoodgail/three-gpu-baker)
- three.js `LightProbeGrid` is "a Light, so adding it to the scene applies its baked irradiance to every lit node material automatically"; multiple volumes can be added per scene — [LightProbeGrid docs](https://threejs.org/docs/pages/LightProbeGrid.html); [three.js PR #33125](https://github.com/mrdoob/three.js/pull/33125)
- Stale-bake fallback pattern (housegen proposal): apply lightmaps and turn real-time fill lights off where a lightmap covers the surface; fall back to real-time lighting when edits make the bake stale — [damhau/housegen issue #42](https://github.com/damhau/housegen/issues/42)
- Runtime probe re-bake scheduling pattern (thirdfold plan): debounce about 500 ms after changes, bake 4–8 probes per frame, crossfade grid intensity over about 600 ms, enable only on high tiers — [thirdfold issue #235](https://github.com/tougenrip/thirdfold/issues/235)
- drei `ContactShadows`: "Since this is a rather expensive effect you can limit the amount of frames it renders when your objects are static", e.g. `frames={1}` — [drei docs: ContactShadows](http://drei.docs.pmnd.rs/staging/contact-shadows)
- drei `AccumulativeShadows`: a planar shadow catcher that accumulates soft shadows and "has zero performance impact after all frames have accumulated"; "If you run 40-100 samples that's usually enough"; pairs with `RandomizedLight` for raycast-like shadows and AO — [drei docs: AccumulativeShadows](http://drei.docs.pmnd.rs/staging/accumulative-shadows)
- drei `BakeShadows` freezes shadow maps (`shadowMap.autoUpdate = false`) for static scenes — [drei docs: BakeShadows](http://drei.docs.pmnd.rs/performances/bake-shadows)
- three.js has had a box-projected cube-map environment mapping example (reported broken in an older issue), showing the technique exists in the WebGL examples lineage — [three.js issue #18111](https://github.com/mrdoob/three.js/issues/18111) (snippet only)

### Inferences
- "Recolourable" lightmaps: three.js's `material.lightMap` contributes indirect diffuse irradiance that the shader multiplies by the material's albedo, so a lightmap baked as irradiance (white or neutral albedo, or the baker's separate direct/indirect channels) lets wall paint and floor material change without a re-bake; only the colour-bleed tint goes stale. This is from my knowledge of the three.js lighting model, not verified against r186 source in this session. Shapespark's real-time material picker on baked scenes is consistent with this approach.
- Recommended hybrid for AI-generated, user-edited rooms (synthesis):
  1. Shell (walls/floor/ceiling): irradiance-only lightmap, baked server-side or in-browser, re-baked only when room dimensions, openings or lights change.
  2. Furniture (movable): lit by a per-room `LightProbeGrid` re-baked incrementally on the client after each edit (about 1–2 s for a room by the estimate in section 1), plus GTAO.
  3. Grounding: `ContactShadows` with `frames={1}` re-triggered on move, or an accumulated shadow catcher (40–100 frames) per room.
  4. Reflections: one cube capture per room, box-projected to the room's known dimensions (the generator knows the box exactly), refreshed on material/object changes as Shapespark 3.6.1 does.
- The weak point of baking furniture occlusion into the shell lightmap is that moving a sofa leaves its baked shadow behind; either exclude furniture from the shell bake (and rely on contact shadows + AO) or accept a re-bake after layout changes.
- A probe-only pipeline (no lightmaps at all) is the minimum viable option and needs no UVs or server; the shell then lacks high-frequency indirect detail (corner darkening, light gradients near windows), part of which GTAO recovers.

### Gaps
- No primary source was found documenting a recolourable/irradiance-only lightmap workflow specifically in three.js r186 (TSL `lightMap` behaviour should be verified in code).
- No current (r186) three.js example or TSL node for box-projected/parallax-corrected environment maps was confirmed; the only evidence is an old issue about a WebGL example.
- No source quantifies the visual gap between probe-lit furniture and fully baked furniture.
- Shapespark's "light probes" are reflection probes; I found no evidence that Shapespark lights dynamic objects with irradiance probes.

## 5. Published comparisons of real-time vs baked lighting for web archviz

### Takeaway
I found no published quantitative comparison (SSIM, PSNR, FLIP or side-by-side screenshots with metrics) of three.js real-time GI against baked lightmaps for interiors, and no 2024–2026 conference talk on the topic. Available evidence is qualitative: practitioners are sceptical of SSGI, a baked-lightmap vendor (Shapespark) keeps investing in Cycles baking, and one team planning the same architecture targets "70–80% of an offline render" with lightmaps.

### Cited Findings
- Practitioner verdict on SSGI: "It's mostly hype at this point" (Usnul, three.js forum, 2025–2026), citing light leaking and only small-scale irradiance — [discourse: SSGI thread](https://discourse.threejs.org/t/ssgi-screen-space-global-illumination/85190)
- A project evaluating the same decision expects baked Cycles lightmaps to reach "roughly 70–80% of an offline render at interactive frame rates" (a target, not a measurement) — [damhau/housegen issue #42](https://github.com/damhau/housegen/issues/42)
- Vendor claim for the real-time side: SSGI yields "realistic color bleeds, soft shadows, and a significantly more natural lighting situation" for architecture, without metrics — [RAVE SPACE blog](https://ravespace.io/blog/webgpu-in-three-js)
- Performance direction: a three.js user reports "crazy bigger fps on mobile" after replacing real-time lights with Blender-baked lightmaps (no numbers) — [discourse: batch lightmap script](https://discourse.threejs.org/t/made-a-blender-script-for-batch-baking-lightmaps-to-optimize-models-for-threejs/82346)
- A reusable measurement harness exists: bhouston/three-gpu-pathtracer-fidelity validates the WebGPU three-gpu-pathtracer against Blender Cycles and the WebGL path tracer at 4096 spp, with images "diffed and scored" and a quality gate on "mean-RMSE threshold, default 1%"; it publishes methodology, not real-time-vs-baked results — [bhouston/three-gpu-pathtracer-fidelity](https://github.com/bhouston/three-gpu-pathtracer-fidelity)
- Market signal: Shapespark (web archviz with baked lighting) shipped Cycles 3.5 → 4.4 baker upgrades, OptiX, light-tree sampling and a real-time bake preview between 2023 and 2026 rather than switching to real-time GI — [Shapespark changelog](https://www.shapespark.com/changelog)

### Inferences
- The team will have to produce its own comparison. A practical protocol: render one generated room four ways (Cycles reference; shell lightmap + probes; LightProbeGrid + GTAO only; SSGI + TRAA) from fixed cameras, score against the Cycles reference with SSIM/FLIP using a fidelity-kit-style harness, and log GPU frame time on one desktop dGPU, one integrated GPU and one phone.
- Given documented SSGI artefacts (leaks through thin geometry, radius-limited influence, TAA ghosting, cost scaling with resolution), interiors with thin walls and large uniformly lit surfaces are a worst case for screen-space GI and a best case for lightmaps/probes.
- "Good enough" likely depends on the product promise: for a planning/editing view, LightProbeGrid + GTAO + contact shadows is defensible and needs no server; for a "final look" or shareable walkthrough, a baked shell lightmap is the established route to photographic indirect light.

### Gaps
- No SSIM/PSNR/FLIP comparisons, benchmark tables or conference talks (SIGGRAPH/Web3D/three.js conf, 2024–2026) on real-time vs baked lighting for web architectural visualisation were found.
- A Qt Quick 3D "SSGI Lightmap Example" surfaced in search (combining SSGI with lightmaps in another engine) but was not read; it may offer a useful non-three.js reference.
- No user-perception study (what end users of room planners accept as "realistic") was found.
