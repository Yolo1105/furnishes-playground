# WebGPU availability and three.js WebGPURenderer WebGL2-fallback limits (as of 2 October 2026)

Source-quality legend used below: **[official]** = vendor release notes, spec-group wiki, project repo/registry/API; **[repo-inspection]** = I read the three.js r186 source or examples directly; **[forum]** = discourse.threejs.org or GitHub issue reporter claims; **[3rd-party]** = blogs/aggregators (treat as unverified).

## 1. WebGPU shipping status per browser and platform in late 2026

### Takeaway
WebGPU is on by default in Chromium (Windows x64, macOS, ChromeOS since 113; Android 12+ since 121; Linux only on Intel Gen12+ and recent NVIDIA since 144/147), Safari 26 (macOS 26, iOS/iPadOS/visionOS 26), and Firefox on Windows (141) and Apple Silicon Macs (145/147). Still not shipped by default: Firefox on Linux, Android and Intel Macs; Chrome on Windows ARM64, most Linux GPUs, Samsung Xclipse GPUs and Android below 12; Safari on anything older than OS 26.

### Cited Findings
Chromium (Chrome, Edge, Opera, Samsung Internet share the Dawn implementation)
- [official] macOS, Windows x86/x64, ChromeOS: shipped in Chromium 113. Android: ARM/Qualcomm/Intel GPUs on Android 12+ in 121; Imagination GPUs on Android 16+ in 139; Samsung Xclipse (Android 12+) and "others" still TBD. Linux: Intel Gen12+ in 144; NVIDIA (driver 535.183.01+ required, Wayland) in 147; other Linux GPUs behind flags (`--enable-unsafe-webgpu --ozone-platform=x11 --use-angle=vulkan --enable-features=Vulkan,VulkanFromANGLE`). Windows ARM64: behind `chrome://flags/#enable-unsafe-webgpu`. — [gpuweb Implementation Status wiki](https://github.com/gpuweb/gpuweb/wiki/Implementation-Status)
- [official] Chrome's own troubleshooting doc (last updated 17 Oct 2025) confirms minimums: Chrome 113+ on ChromeOS/macOS/Windows, Chrome 121+ on Android; it still describes Linux as needing `#enable-unsafe-webgpu` and `#enable-vulkan` (predates the 144/147 Linux rollouts). — [Chrome WebGPU troubleshooting tips](https://developer.chrome.com/docs/web-platform/webgpu/troubleshooting-tips)
- [official-ish] caniuse data: Chrome 113+ = supported with notes "Not enabled on Linux by default" (#5) and, from 144, "Support on Linux depends on hardware and drivers" (#9); Edge 113+ supported; Opera 99+; Opera Mobile 80+; Samsung Internet 24+; Chrome for Android supported (caniuse tracks only the current version, 154). - [official] Chrome for Android on WebGPU was announced January 2024 (Chrome 121). — [HN thread linking the Chrome announcement](https://news.ycombinator.com/item?id=39045598)

- [3rd-party, unverified] One aggregator claims "Android WebView and iOS WKWebView do not ship WebGPU on by default, so hybrid apps still need a fallback". — [TestMu learning hub](https://www.testmuai.com/learning-hub/webgpu-browser-support/)

### Inferences
- A practical support matrix for a consumer interior viewer: Windows/macOS/ChromeOS desktop on current Chrome/Edge/Safari 26/Firefox = WebGPU; iPhone/iPad on iOS 26+ = WebGPU; Android 12+ flagship/midrange with Adreno/Mali = WebGPU; everything else (older iOS, Macs not on macOS 26 using Safari, Firefox Linux/Android, Linux desktops outside Intel Gen12+/NVIDIA, Exynos-Xclipse Galaxy phones, Windows-on-ARM Chrome) = WebGL2 fallback.
- iOS/iPadOS support is OS-gated, not browser-gated: users on iOS 18 or earlier have no WebGPU regardless of browser, because all iOS browsers historically use WebKit.
- The TestMu claim about WKWebView/Android WebView conflicts with how engine-level features normally propagate (Android WebView is Chromium; WKWebView is WebKit). Treat in-app browser (Instagram, TikTok, WeChat, LINE) support as unknown and feature-detect at runtime.

### Gaps
- Exact stable release dates for Chrome 113 (I recall May 2023), Chrome 139, Chrome 144 and Chrome 147 (I estimate roughly Jan and Apr 2026) were not confirmed from a primary source in this session; the wiki gives versions only.
- Safari 26.0 release day (I recall 15 Sept 2025) was not re-verified; the WebKit post confirms the version and platforms only.
- Samsung Internet 24 release date not found; WebGPU status on Xclipse (Exynos 2200/2400) devices is "TBD" on the gpuweb wiki with no date.
- No authoritative statement found on WebGPU inside Android WebView, WKWebView, or specific in-app browsers.
- Whether Firefox Linux/Android will actually ship in Q4 2026 is unconfirmed; only the "targets 2026" statement exists.

## 2. Estimated share of users with WebGPU; blocklists

### Takeaway
Browser-version-based estimates put WebGPU at about 86–89% of global users (caniuse, Aug–Oct 2026), but measured working-adapter rates are lower: Web3D Survey reports about 82% overall, with Android about 74%, iOS about 87%, Windows about 87%, macOS about 89% and Linux about 17%. Plan for roughly 13–18% of sessions landing on WebGL2 overall, and about a quarter of Android sessions.

### Cited Findings
- [official-ish] caniuse global usage: 85.72% full support. Partial-support figure conflicts between two reads of the same dataset: the page render gave "85.72% + 1.63% = 87.35%", the raw JSON gave `usage_perc_a: 3.05` (total 88.77%). — [caniuse page](https://caniuse.com/webgpu); [caniuse raw JSON](https://raw.githubusercontent.com/Fyrd/caniuse/main/features-json/webgpu.json)
- [3rd-party] Utsubo (updated 24 Sept 2026) cites "about 87% (84% full plus 3% partial, data from August 2026)". — [Utsubo migration guide](https://www.utsubo.com/blog/webgpu-threejs-migration-guide)
- [survey] Web3D Survey: 82.21% of reports returned a working WebGPU adapter (0.04% fallback/software adapters). By platform: Windows 86.84%, macOS 89.07%, ChromeOS 91.9%, iOS 86.64%, Android 74.31%, Linux 16.68%. By browser: Edge 92.85%, Opera 88.64%, Chrome/Chromium 83.6%, Safari 80.86%, Samsung Internet 77.58%, Firefox 58.76%, Other 80.14%. (A search snapshot days earlier showed 82.17% / Android 73.95% / iOS 87.01%, so figures move slightly.) Sampling window and sample size are not stated on the page. — [Web3D Survey WebGPU](https://web3dsurvey.com/webgpu)
- [official] Chrome lists reasons `requestAdapter()` returns null: hardware acceleration disabled by the user, platform not yet supported, "GPU hardware specifically blocklisted" (overridable with `#enable-unsafe-webgpu`), incompatible adapter options, no GPU available, or GPU process crashes. — [Chrome troubleshooting tips](https://developer.chrome.com/docs/web-platform/webgpu/troubleshooting-tips)
- [official] Linux blocklist shape: only Intel Gen12+ and NVIDIA with driver ≥ 535.183.01 are enabled in Chrome; AMD and older Intel on Linux remain flag-only. — [gpuweb wiki](https://github.com/gpuweb/gpuweb/wiki/Implementation-Status)
- [3rd-party, unverified] "Chrome 142 added many GPUs to the WebGPU blocklist for stability reasons". — [any3d.cc troubleshooting blog](https://any3d.cc/en-US/blog/fix-webgpu-unavailable)
- [repo-inspection] three.js `SSGINode` logs an error on the WebGPU backend when the device lacks the optional `rg11b10ufloat-renderable` feature ("required for SSGI"), so having WebGPU does not guarantee every effect. — [SSGINode.js r186](https://raw.githubusercontent.com/mrdoob/three.js/r186/examples/jsm/tsl/display/SSGINode.js)

### Inferences
- caniuse counts browser versions, not working adapters; Web3D Survey measures actual `requestAdapter()` success but on a self-selected set of 3D sites. The true figure for a consumer furniture/interior audience is probably between them: about 82–87% WebGPU, 13–18% WebGL2 fallback.
- Desktop vs mobile split (derived from Web3D Survey platform rows): desktop Windows/macOS about 87–89%; mobile iOS about 87% and Android about 74%. Android is the main fallback population (Android below 12, Xclipse, Imagination below Android 16, Firefox Android, blocklisted drivers).
- Firefox users are the weakest desktop segment (about 59% working adapters) because Linux, Intel Mac and Android builds are off by default.
- "No path-tracing support" equals "no WebGPU" (see section 3: the current three-gpu-pathtracer requires WebGPU compute), so about 13–18% of users overall and about 26% of Android users would have no path-traced mode.

### Gaps
- No StatCounter-derived desktop/mobile WebGPU split found; caniuse does not publish one.
- No published percentage of Chrome users hit by the GPU blocklist.
- Share of WebGPU devices exposing `rg11b10ufloat-renderable` (needed by SSGINode) not retrieved; Web3D Survey has per-feature pages that could answer it.
- Web3D Survey methodology (date range, sample size) not disclosed on the page fetched.

## 3. three.js WebGPURenderer: release history through r186, WebGL2 backend coverage, stability

### Takeaway
r186 (npm 0.186.0 on 8 Sept 2026; 0.186.1 on 24 Sept 2026) is the current release; `WebGPURenderer` auto-falls back to a WebGL2 backend, and raster features, node materials and `RenderPipeline` effects (GTAO, SSR, SSGI, TRAA, LightProbeGrid) are written to run on both, while true compute features (storage textures, indirect dispatch/draw, workgroup/atomics, VXGI, compute rasterizer, the WebGPU path tracer) are WebGPU-only. The renderer is still churning: each release has breaking changes and a steady stream of WebGL-backend-specific bugs.

### Cited Findings
Release dates
- [official] npm `three`: 0.180.0 3 Sep 2025; 0.181.0 31 Oct 2025; 0.182.0 10 Dec 2025; 0.183.0 18 Feb 2026; 0.184.0 16 Apr 2026; 0.185.0 25 Jun 2026 (0.185.1 on 1 Jul 2026); 0.186.0 8 Sep 2026; 0.186.1 24 Sep 2026. GitHub release objects carry the date of the latest patch (r186 shows 24 Sep 2026, r185 1 Jul 2026, r184 16 Apr 2026, r183 20 Feb 2026). — [npm registry: three](https://registry.npmjs.org/three), [GitHub releases](https://github.com/mrdoob/three.js/releases)

Migration-relevant changes (official migration guide)
- [official] r181: `renderAsync()`/`computeAsync()` deprecated (use sync versions after init); `waitForGPU()` removed. r182: `colorBufferType` renamed `outputBufferType`. r183: "PostProcessing has been renamed to RenderPipeline"; SSRNode blend changed; shadows reworked (bias values may need retuning); `WebGLCubeRenderTarget` no longer usable with WebGPURenderer. r185: premultiplied-alpha handling changed; GTAONode "computes now a more physically correct ambient occlusion" (darker); `AnamorphicNode` removed. r186: "LightProbeGrid has been renamed to LightProbeGridWebGL" (the `LightProbeGrid` name now refers to the new WebGPURenderer version); "PCFSoftShadowMap with WebGPURenderer has been removed"; GTAONode `distanceExponent`/`distanceFallOff` deprecated; light registration changed to `CustomLight.registerNode()`; `Object3D.dispose()` added. — [three.js Migration Guide](https://github.com/mrdoob/three.js/wiki/Migration-Guide)
- [official] r186 release notes include: LightProbeGrid "Add WebGPURenderer version" (#33913) and "Support incremental baking" (#34486); GTAONode rework (#33895, #33903, #33919, #33930, #33931); `SSAONode` and `depthAwareBlur` (#33921); `DirectRenderPipeline` (#34166); `OITPassNode` (#34253); `TAAUtils` shared functions (#34458); SSRNode clean-up (#34377); `compileComputeAsync()` (#32551); SunLight support (#34259); a Gaussian splat renderer; WebGLBackend fixes (#34142, #34146, #34502). — [r186 release](https://github.com/mrdoob/three.js/releases/tag/r186)

What the WebGL2 backend does and does not do
- [official] Class doc: "By default, the renderer tries to use a WebGPU backend if the browser supports WebGPU. If not, WebGPURenderer falls backs to a WebGL 2 backend." `forceWebGL: true` forces the WebGL2 backend; the fallback logs "WebGPURenderer: WebGPU is not available, running under WebGL2 backend." — [WebGPURenderer.js r186](https://raw.githubusercontent.com/mrdoob/three.js/r186/src/renderers/webgpu/WebGPURenderer.js)
- [repo-inspection] Compute on the WebGL2 backend is emulated with transform feedback (`gl.beginTransformFeedback(gl.POINTS)` in `WebGLBackend.compute()`); array/indirect dispatch counts are rejected with warnings ("count parameter must be a single number, not IndirectStorageBufferAttribute"); storage buffers are emulated through PBO/texture reads in `GLSLNodeBuilder`. So simple per-element `instancedArray` compute works; grid/workgroup-style compute does not. — [WebGLBackend.js r186](https://raw.githubusercontent.com/mrdoob/three.js/r186/src/renderers/webgl-fallback/WebGLBackend.js), [GLSLNodeBuilder.js r186](https://raw.githubusercontent.com/mrdoob/three.js/r186/src/renderers/webgl-fallback/nodes/GLSLNodeBuilder.js)
- [repo-inspection] Of 230 `webgpu_*` examples in r186, the ones that hard-require WebGPU (`WebGPU.isAvailable() === false` then throw 'No WebGPU support') are: compute_birds, compute_cloth, compute_particles_fluid, compute_rasterizer, compute_rasterizer_ibl, compute_reduce, compute_sort_bitonic, compute_texture, compute_texture_3d, compute_texture_pingpong, compute_water, hdr, lights_clustered, materials, materials_retroreflection, multiple_canvas, particles, skinning_instancing_individual, struct_drawindirect, tsl_interoperability, tsl_vfx_linkedparticles, vxgi, vxgi_sponza, volume_fire. Not gated (written to run on either backend): `webgpu_postprocessing_ssgi`, `_ssr`, `_ssr_denoise`, `_traa`, `_ao`, `webgpu_upscaling_taau`, `webgpu_lightprobes*`, `webgpu_gaussian_splat`, `webgpu_compute_particles`, `webgpu_compute_points`, `webgpu_storage_buffer`. — [three.js r186 examples directory](https://github.com/mrdoob/three.js/tree/r186/examples)
- [repo-inspection] `LightProbeGrid.bake()` throws "requires a WebGPURenderer. For WebGLRenderer, use LightProbeGridWebGL" — it requires the renderer class, not the WebGPU backend. — [LightProbeGrid.js r186](https://raw.githubusercontent.com/mrdoob/three.js/r186/examples/jsm/lighting/LightProbeGrid.js)
- [repo-inspection] `TRAANode` contains a WebGPU-specific workaround (history/depth size mismatch on resize "does not happen with the WebGL backend"); `SSRNode` warns that its environment fallback needs an equirectangular HDR with CPU-side data (PMREM cubemaps / `scene.environment` unsupported). — [TRAANode.js r186](https://raw.githubusercontent.com/mrdoob/three.js/r186/examples/jsm/tsl/display/TRAANode.js), [SSRNode.js r186](https://raw.githubusercontent.com/mrdoob/three.js/r186/examples/jsm/tsl/display/SSRNode.js)
- [3rd-party] Utsubo's r186 checklist: unavailable on the WebGL2 fallback are indirect compute dispatch and indirect draws (`geometry.setIndirect()`), workgroup shared memory, and storage textures (`textureStore()`); available on both are built-in and node materials, `RenderPipeline` post-processing, and compute via `renderer.compute()` + `instancedArray`. `ShaderMaterial`, `RawShaderMaterial` and `onBeforeCompile` work on neither backend. Check the backend with `renderer.backend.isWebGPUBackend` after init. — [Utsubo migration guide](https://www.utsubo.com/blog/webgpu-threejs-migration-guide)
- [official] Path tracing: three-gpu-pathtracer merged "WebGPU Support" (PR #713) on 28 Sept 2026 and published 0.0.25 (28 Sept) / 0.0.26 (29 Sept 2026); README now describes it as using "WebGPU compute shaders", imports `WebGPUPathTracer` from `three-gpu-pathtracer/webgpu`, and lists "The project requires WebGPU" as the first gotcha; only MeshStandard/MeshPhysical materials are supported. — [three-gpu-pathtracer README](https://github.com/gkjohnson/three-gpu-pathtracer), [PR #713](https://github.com/gkjohnson/three-gpu-pathtracer/pull/713), [npm registry](https://registry.npmjs.org/three-gpu-pathtracer)

Stability: open and recent issues (GitHub, as of 2 Oct 2026)
- [official tracker] Open: #30560 "Current UBO system has severe performance issues with many render items" (High priority, opened 19 Feb 2025, 50 comments, last updated 15 Sep 2026); #33821 "Material initialization is extremely slow compared to WebGLRenderer" (16 Jun 2026); #33795 "StorageTexture compute writes not visible to RenderPipeline texture() bindings in same frame" (12 Jun 2026); #34720 "a failed node build silently falls back to a bare NodeMaterial" (30 Sep 2026); #32527 "Reuses the same shader regardless of bone count"; #29980 "Models with morphs are less performant"; #27570 "Camera nodes are broken in compute shaders" (WebGL Backend label, open since Jan 2024); #29781 "Need a Raw Shader solution for WebGPURenderer". — [three.js issues: WebGPURenderer](https://github.com/mrdoob/three.js/issues?q=is%3Aissue+is%3Aopen+WebGPURenderer+in%3Atitle)
- [official tracker] WebGL-backend-specific bugs filed during the r185/r186 cycle (now closed): #34597 "WebGL2 fallback never deletes a GL program, shader or VAO" (17 Sep 2026); #34196 "Skinned meshes with large skeletons fail to link on the WebGL 2 backend" (9 Aug 2026); #34145 "MinEquation/MaxEquation not supported by the WebGL backend" (30 Jul 2026, fixed by #34146 in r186); #34118 `copyTextureToBuffer` on 3D/array textures; #33009 "InstanceNode UBO exceeds GL_MAX_UNIFORM_BLOCK_SIZE on Chrome/ANGLE for 256+ instances" (16 Feb 2026); #33573 "TSL drawIndex accessor has no fallback when WEBGL_multi_draw is unavailable" (closed Won't fix); #34646 "a geometry's buffers are only freed on its first dispose()" (24 Sep 2026); #34211 BatchedMesh index-offset bug (fixed by #34212 in r186). — [three.js issue #34597](https://github.com/mrdoob/three.js/issues/34597), [#34196](https://github.com/mrdoob/three.js/issues/34196), [#33009](https://github.com/mrdoob/three.js/issues/33009), [#33573](https://github.com/mrdoob/three.js/issues/33573)
- [official tracker] #34551 (r186-era): a TextureNode built with an unfilterable texture compiles to `textureLoad` with no sampler and keeps that after a filterable texture is assigned. — [three.js issue #34551](https://github.com/mrdoob/three.js/issues/34551)

### Inferences
- For the stated stack (r186, TSL node materials, `RenderPipeline` with GTAO/SSR/SSGI/TRAA, LightProbeGrid), nothing is *structurally* blocked on the WebGL2 backend: these are fragment-shader/MRT effects and their official examples are not WebGPU-gated. What is blocked on fallback is anything built on storage textures, indirect dispatch, atomics, VXGI, or the WebGPU path tracer.
- "Works" is not "fast": SSGI + SSR + TRAA is a heavy MRT/half-float pipeline; the default `outputBufferType` is `HalfFloatType`, and WebGL2 fallback users are disproportionately older/low-end devices. A reduced effect tier for `isWebGPUBackend === false` is the prudent design. I found no official per-effect performance numbers for the WebGL2 backend.
- The WebGL backend receives fewer eyes than the WebGPU backend: several r185/r186 bugs (resource leaks, skeleton link failures, UBO size limits) were WebGL-backend-only and found by users, so the fallback path needs its own QA with `forceWebGL: true`.
- Pinning an exact three version matters: r181–r186 each changed WebGPURenderer APIs or visual output (shadows, AO darkness, premultiplied alpha, light probes).

### Gaps
- The official manual page (threejs.org/manual/en/webgpurenderer.html) returned 404 in this session, so its wording on "experimental" status and fallback limits is quoted only via search snippets ("still in an experimental state… you may find better performance with WebGLRenderer"), not verified.
- No official feature matrix exists listing which TSL display nodes are tested on the WebGL2 backend; the statement that SSGI/SSR/TRAA/GTAO run on fallback rests on example gating and source reading, not on a maintainer statement or a test run.
- Whether #34597/#34646 fixes landed in 0.186.1 or only on dev was not checked.
- Whether three-gpu-pathtracer 0.0.25+ still exports the older WebGL2 `WebGLPathTracer` was not checked; 0.0.24 (21 Feb 2026) and earlier were WebGL2-based.

## 4. React Three Fiber v9 with WebGPURenderer and drei

### Takeaway
R3F v9 (latest 9.8.1, 24 Sept 2026) supports WebGPURenderer only through an async `gl` factory plus `extend(THREE)` from `three/webgpu`; issue #3782 (double factory invocation on re-render, corrupting the renderer) is still open with an unmerged fix PR. First-class WebGPU support is being built in R3F v10 and drei v11, both still alpha; drei v10 components that patch GLSL (Text, MeshTransmissionMaterial, EffectComposer-based helpers) do not work under WebGPURenderer.

### Cited Findings
- [official] npm `@react-three/fiber`: 9.0.0 19 Feb 2025; 9.6.1 28 Apr 2026; 9.7.0 31 Jul 2026; 9.8.0 22 Sep 2026; 9.8.1 24 Sep 2026 (`latest`). v10: 10.0.0-alpha.0 14 Jan 2026 … alpha.5 8 Sep 2026; canary builds published daily through 2 Oct 2026. — [npm registry: @react-three/fiber](https://registry.npmjs.org/@react-three%2Ffiber)
- [official] v9 migration guide: the Canvas `gl` prop accepts "a promise for async constructors like WebGPURenderer"; documented pattern is `gl={async (props) => { const renderer = new THREE.WebGPURenderer(props as any); await renderer.init(); return renderer }}` with `import * as THREE from 'three/webgpu'`, `extend(THREE as any)` and `ThreeToJSXElements<typeof THREE>` for types. It warns the renderer is "still a work in progress and not fully backward-compatible with all of Three's features". — [R3F v9 migration guide](https://r3f.docs.pmnd.rs/tutorials/v9-migration-guide)
- [official tracker] Issue #3782 "Re-render during async gl factory invokes it twice and corrupts the renderer": opened 13 Jul 2026 against R3F 9.6.1 / three 0.185.1; state open as of 2 Oct 2026. `configure()` runs on every layout effect and checks `if (!state.gl)` before awaiting the factory, so a parent re-render during the pending promise invokes the factory again; result is two renderers on one canvas, the unsized one keeping a 300×150 depth buffer and producing per-frame "depth stencil attachment size does not match" errors; the reporter also traces silent WebGPU canvas death on client-side navigation in static exports to this race. Fix PR #3783 ("don't re-enter configure() while an async gl factory is pending", opened 13 Jul 2026) is open and unmerged. — [R3F issue #3782](https://github.com/pmndrs/react-three-fiber/issues/3782), [PR #3783](https://github.com/pmndrs/react-three-fiber/pull/3783)
- [official tracker] Other WebGPU issues: #3752 "Data races when using WebGPU"; v10-only: #3926 "R3F-created WebGPURenderer is not disposed on unmount" (closed 23 Sep 2026), #3965 "under the WebGL2 fallback, a secondary canvas draws into the primary's canvas" (closed 26 Sep 2026), #3846 "/webgpu entry throws … under Turbopack" (closed 9 Aug 2026), #3850 "suspending inside Canvas re-creates the whole renderer root" (closed), #3798 "repeatable browser/WebGPU validation harness" (open, beta milestone). v10 introduces `useRenderPipeline`, `useLocalNodes`, `useGPUStorage` and a `renderer` prop. — [R3F issue #3752](https://github.com/pmndrs/react-three-fiber/issues/3752), [#3926](https://github.com/pmndrs/react-three-fiber/issues/3926), [R3F issues search](https://github.com/pmndrs/react-three-fiber/issues?q=is%3Aissue+WebGPU)
- [official] npm `@react-three/drei`: 10.7.8 5 Aug 2026; 10.7.9 25 Sep 2026 (`latest`); 11.0.0-alpha.1 14 Jan 2026 … alpha.7 5 Sep 2026. — [npm registry: @react-three/drei](https://registry.npmjs.org/@react-three%2Fdrei)
- [official tracker] drei v11 splits into `src/legacy` (WebGL) and `src/webgpu`; open v11 issues show the port is incomplete: #2842 "Environment gainmap loading throws on WebGPU — gainmap-js calls readRenderTargetPixels"; #2818 "Four root-exported components are classified agnostic but are WebGL-only"; #2811 "webgpu/BlurPass is still the WebGL implementation"; #2810 WebGPU Caustics incomplete; #2803 "Don't ship broken: stub every WebGPU component that doesn't work"; #2843 "16 legacy stories run WebGL-only components on the WebGPU renderer"; unverified on WebGPU: RenderTexture (#2822), View (#2821), Hud (#2820), Fisheye (#2824), useDepthBuffer (#2825). Closed: #2809 "Preload does nothing on WebGPU — gl.compile() is an async alias there". — [drei issues: WebGPU](https://github.com/pmndrs/drei/issues?q=is%3Aissue+WebGPU)
- [3rd-party test] Utsubo tested drei 10.7.8 + R3F 9.8.0 + r186: OrbitControls and Html worked on both backends; Environment (preset) worked on both; Environment with children/cube map worked on WebGPU only ("WebGL 2 rendered no reflections"); Text not supported (troika patches shaders via `onBeforeCompile`); EffectComposer (@react-three/postprocessing) not supported. — [Utsubo migration guide](https://www.utsubo.com/blog/webgpu-threejs-migration-guide)
- [forum] drei `MeshTransmissionMaterial` stopped working with three 0.180.0 under WebGPU because its `DiscardMaterial` is a `ShaderMaterial`. — [three.js forum: Drei MeshTransmissionMaterial WebGPU](https://discourse.threejs.org/t/drei-meshtransmissionmaterial-webgpu/87427)

### Inferences
- On R3F v9, the safest pattern is to create and `await init()` the renderer in a memoised promise outside React's render path (or guard the factory with a module-level/ref-cached promise) so re-renders cannot trigger a second construction; avoid state updates in ancestors while the canvas boots. This works around #3782 until PR #3783 or v10 ships.
- drei rule of thumb under WebGPURenderer: controls, DOM overlays, loaders (`useGLTF`), cameras, bounds and plain-geometry helpers work; anything that injects GLSL (`shaderMaterial`, `MeshTransmissionMaterial`, `MeshReflectorMaterial`, `Text`, `Sparkles`, `Caustics`, `ContactShadows`/`AccumulativeShadows` blur materials, `Outlines` in v10) or depends on `WebGLRenderTarget` internals should be assumed broken until tested. The second half of this list is my extrapolation from the `ShaderMaterial`/`onBeforeCompile` rule; only Text, EffectComposer, MeshTransmissionMaterial and Environment-with-children were confirmed by sources.
- Post-processing must move from `@react-three/postprocessing` (EffectComposer) to three's `RenderPipeline` with TSL nodes, driven from `useFrame` at priority 1 in v9, or `useRenderPipeline` in v10.

### Gaps
- No maintainer comment on #3782 was visible; unknown whether 9.8.x contains a partial mitigation (the PR is unmerged).
- No official drei v10 compatibility list for WebGPURenderer exists; drei v11 status files were reported as inconsistent in drei issue #2806.
- No release date for R3F v10 or drei v11 stable found.

## 5. Performance: WebGPU vs WebGL2 in three.js for PBR scenes

### Takeaway
There is no evidence that swapping to WebGPURenderer speeds up a typical PBR scene; maintainers say not to expect it, and open issues show WebGPURenderer is slower for many separate meshes (about 2–4x in reported cases) and for material initialisation (16–36x in one report). WebGPU's gains come from compute, instancing/batching and lower memory, not from draw-call-heavy scene graphs.

### Cited Findings
- [forum, maintainer] donmccurdy (2–3 Sep 2025): "I would not expect performance improvement simply by swapping WebGPURenderer in for WebGLRenderer today." Same thread: a user rendering 10,000 cylinders saw no FPS gain but about 30% lower memory with WebGPURenderer. — [three.js forum: Understanding about WebGPURenderer](https://discourse.threejs.org/t/understanding-about-webgpurenderer/86635)
- [forum + tracker] r173, Chrome on M1 Pro, 20,000 non-instanced cubes: WebGLRenderer about 60 FPS vs WebGPURenderer about 15 FPS (Feb 2025). Mugen87's diagnosis: each object uses its own UBO, causing excessive `setBindGroup()`/`writeBuffer()` calls. Tracked as #30560, still open and High priority (last activity 15 Sep 2026). — [forum thread](https://discourse.threejs.org/t/why-webgpurenderer-performance-significantly-lower-than-webglrenderer/77629), [issue #30560](https://github.com/mrdoob/three.js/issues/30560)
- [tracker, reporter claim] #33821 (16 Jun 2026, dev branch): initialising 10,000 meshes took about 2,100 ms on WebGPURenderer vs 131 ms on WebGLRenderer with a material per mesh (about 16x), and about 1,029 ms vs 28 ms with one shared material (about 36x). Open, no maintainer reply seen. — [issue #33821](https://github.com/mrdoob/three.js/issues/33821)
- [tracker, reporter claim] Mobile: on a Samsung Galaxy S20 FE the BatchedMesh example ran about 13 FPS on WebGPU vs about 25 FPS on WebGL (Oct 2024); issue still open. — [issue #29580](https://github.com/mrdoob/three.js/issues/29580)
- [3rd-party] ICS Media (r176, May 2025): at 60 FPS with separate meshes, WebGLRenderer sustained 2,562 boxes vs 682 for WebGPURenderer (about 4x). — [ICS Media](https://ics.media/en/entry/250501/)
- [3rd-party] Utsubo (Sept 2026): "WebGPU isn't universally faster"; advises profiling before migrating for speed; gives no numbers. — [Utsubo migration guide](https://www.utsubo.com/blog/webgpu-threejs-migration-guide)
- [official] r184 notes claim TSL compilation became about 3x faster. — [three.js releases](https://github.com/mrdoob/three.js/releases)

### Inferences
- An interior viewer (tens to low hundreds of furniture meshes, PBR materials, shadows, AO/SSR) is draw-call-light, so the per-object UBO overhead is unlikely to dominate; cost will be driven by post-processing passes and half-float render targets, which are similar on both backends.
- First-load shader/material compile time is a real risk on WebGPURenderer (node graph build per material); merging materials, `compileAsync`, and avoiding per-mesh material clones matter more than under WebGLRenderer.
- No source compares the *WebGL2 backend of WebGPURenderer* against classic `WebGLRenderer`; fallback users may get worse performance than they would have on WebGLRenderer, since the fallback is a less-optimised path (see leaks/limits in section 3).

### Gaps
- No rigorous 2026 benchmark of WebGPU backend vs WebGL2 backend vs WebGLRenderer for a PBR interior-type scene, on desktop or mobile, was found. All numbers above are stress tests with thousands of meshes, mostly from 2024–2025.
- No iOS (Safari 26) three.js WebGPU performance data found.
- No published frame-time cost for SSGI/SSR/TRAA/GTAO per backend.

## 6. Production three.js sites using WebGPURenderer

### Takeaway
Named production uses exist but are mostly agency/brand showcase sites and a few tools, all reported by third parties or forum posts; I found no large e-commerce or interior/furniture configurator publicly confirmed on WebGPURenderer.

### Cited Findings
- [3rd-party, self-reported] Utsubo lists: "Waves of Connection" (Expo 2025 Osaka; WebGPU particle simulation of up to about one million particles), Vectr (WebGPU 3D hero with WebGL fallback), and Segments.ai (LiDAR point-cloud labelling platform migration). — [Utsubo migration guide](https://www.utsubo.com/blog/webgpu-threejs-migration-guide)
- [3rd-party] IVRESS brand experience: FWA Site of the Month May 2026, uses WebGPURenderer with WebGL fallback and TSL shaders. — [Utsubo: Best Three.js Websites 2026](https://www.utsubo.com/blog/best-threejs-websites-2026)
- [forum] shader.se studio site built with WebGPURenderer and TSL, rendering UI in-canvas via a fork of pmndrs/uikit patched for WebGPU. — [three.js forum showcase](https://discourse.threejs.org/t/our-80s-corporate-satire-studio-site-using-webgpurenderer-and-tsl/92271)
- [forum] Interactive 3D scene showcase built on WebGPURenderer + TSL (4,000 compute-driven particles). — [three.js forum showcase](https://discourse.threejs.org/t/interactive-3d-scene-built-with-three-js-webgpu-and-tsl/90492)
- [official] WebKit named Three.js among engines that "work great in Safari 26.0" with WebGPU. — [WebKit Features in Safari 26.0](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/)

### Inferences
- Adoption is real but concentrated in effects-led marketing sites where compute/TSL is the draw. A product-critical interior viewer on WebGPURenderer + R3F would be relatively early; the dependency chain (R3F v10 alpha, drei v11 alpha, three-gpu-pathtracer WebGPU released days ago) is not yet stable.

### Gaps
- None of these sites' renderer choice was independently verified (e.g. by inspecting their bundles).
- No list of production WebGPURenderer users is maintained by the three.js project; no furniture/interior/real-estate example found.
