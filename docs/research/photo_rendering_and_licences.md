# Photo-quality still rendering (browser path tracing vs server Cycles) and reference-repository licences

Research date: 2 October 2026. All GitHub facts below were read from the repositories (README, LICENSE, releases, issues) or the GitHub/npm public APIs on that date. Text is paraphrased unless in quotation marks. Licence notes report what the repositories state and are not legal advice.

## A1. three-gpu-pathtracer (gkjohnson): releases, WebGPUPathTracer vs WebGLPathTracer, API, open issues, browser support, render time

### Takeaway
`WebGPUPathTracer` shipped four days ago (v0.0.25 on 28 Sep 2026, hotfix v0.0.26 on 29 Sep 2026), with `WebGLPathTracer` deprecated in the same release; it is feature-rich (area/punctual/IES lights, env-map MIS, sheen/clearcoat/transmission/dispersion, built-in OIDN and FSR hooks) but very new, with open bugs and no published benchmark numbers. Render time for 1080p/4K at 256 spp is therefore an estimate, not a measured figure.

### Cited Findings

Release history
- v0.0.26 published 29 Sep 2026: fixes an import with a missing file extension that broke loading the WebGPU path tracer from a CDN — [GitHub releases](https://github.com/gkjohnson/three-gpu-pathtracer/releases); [CHANGELOG](https://github.com/gkjohnson/three-gpu-pathtracer/blob/main/CHANGELOG.md)
- v0.0.25 published 28 Sep 2026: adds `WebGPUPathTracer` (imported from `three-gpu-pathtracer/webgpu`), raises the minimum three.js to r185, and deprecates `WebGLPathTracer` (to be removed in a future release) — [GitHub releases](https://github.com/gkjohnson/three-gpu-pathtracer/releases)
- v0.0.24 published 21 Feb 2026 (bug fixes; minimum three.js r180; RGBELoader replaced by HDRLoader). Before that, v0.0.23 was 7 Jun 2024, so there was a ~20-month gap with no release — [GitHub releases](https://github.com/gkjohnson/three-gpu-pathtracer/releases); npm publish timestamps agree: 0.0.24 on 2026-02-21, 0.0.25 on 2026-09-28, 0.0.26 on 2026-09-29, `latest` = 0.0.26 — [npm registry](https://registry.npmjs.org/three-gpu-pathtracer)
- Earlier milestones: v0.0.21 (29 Apr 2024) introduced the `WebGLPathTracer` class and TypeScript definitions; v0.0.17 (18 Jan 2024) fixed crashes on macOS, Android and iOS — [GitHub releases](https://github.com/gkjohnson/three-gpu-pathtracer/releases)
- The WebGPU work was PR #713 "WebGPU Support", opened 4 Feb 2026 and merged 28 Sep 2026 — [PR #713](https://github.com/gkjohnson/three-gpu-pathtracer/pull/713)
- The maintainer announced on 9 Jul 2026 that the WebGL tracer would be deprecated and removed because maintaining it across platforms was too much effort; WebGL will not be supported through either `WebGLRenderer` or `WebGPURenderer`'s WebGL backend, and the WebGL version remains usable at the last release before removal — [Issue #779](https://github.com/gkjohnson/three-gpu-pathtracer/issues/779)
- `package.json` at v0.0.26: licence MIT; peer dependencies `three >=0.185.0`, `three-mesh-bvh >=0.9.15`, `xatlas-web ^0.1.0`; the root entry still exports the (deprecated) WebGL code and `./webgpu` exports the new one — [package.json](https://github.com/gkjohnson/three-gpu-pathtracer/blob/main/package.json)
- Repository is active: last push 30 Sep 2026; ~1,890 stars; an "Unreleased" changelog section already lists two more WebGPU fixes (black output after changing `maxBounces`/`maxTransparentBounces` once the render has settled; a memory leak on every reset, scene change and dispose) — [CHANGELOG](https://github.com/gkjohnson/three-gpu-pathtracer/blob/main/CHANGELOG.md)

What WebGPUPathTracer supports (as of v0.0.26)
- README now describes the project as using three-mesh-bvh and WebGPU compute shaders; the current "Gotchas" are: WebGPU required; spot/directional/point lights only supported with MIS; only `MeshStandardMaterial` and `MeshPhysicalMaterial` supported; emissive materials supported but without MIS; upscaling does not work with a transparent background — [README](https://github.com/gkjohnson/three-gpu-pathtracer/blob/main/README.md)
- Maintainer's list of already-implemented WebGPU features (comment of 5 Jul 2026, edited since): wavefront and megakernel modes; opaque standard-material properties; environment-map lighting and background; equirectangular rendering; depth of field/bokeh; Sobol sampling; transparent background; mobile support; HDR; texture atlas; instances and BatchedMesh; SkinnedMesh; multi-UV; material arrays and sidedness; texture transforms and filtering; anisotropy; sheen; specular colour/intensity; opaque dielectric IOR; improved energy conservation for dielectric/metallic/clearcoat; next-event estimation with MIS; Russian roulette; firefly clamping; thin-wall and volume transmission; "matte" objects; FidelityFX upscaler; OIDN denoiser; EON diffuse model; directional and point lights; area lights; IES spotlight profiles; dispersion — [Issue #777, first comment](https://github.com/gkjohnson/three-gpu-pathtracer/issues/777)
- README demo list includes dedicated area-light, spot-light, "Denoising and Upscaling", interior-scene equirect, depth-of-field and animation-rendering examples — [README](https://github.com/gkjohnson/three-gpu-pathtracer/blob/main/README.md)
- The `./webgpu` entry exports `WebGPUPathTracer`, `BlurredEnvMapGenerator`, constants, `RenderToScreenMaterial`, `OIDNDenoiser`, `FSRUpscaler`, and shims that make `EquirectCamera`, `PhysicalCamera` and `ArrayCamera` work — [src/webgpu/index.js](https://github.com/gkjohnson/three-gpu-pathtracer/blob/main/src/webgpu/index.js)

What the older WebGLPathTracer had / lacked (v0.0.24 README)
- WebGL 2 based; listed features: GGX surface model, textures, normal maps, emission, environment maps, tiled rendering. Documented exports included `PhysicalCamera`, `EquirectCamera`, `PhysicalSpotLight` (with IES map), `ShapedAreaLight`, `BlurredEnvMapGenerator`, `GradientEquirectTexture`, `FogVolumeMaterial`, `DenoiseMaterial`, `CompatibilityDetector` — [README at v0.0.24](https://github.com/gkjohnson/three-gpu-pathtracer/blob/v0.0.24/README.md)
- WebGL-era restrictions that are absent from the current gotcha list: all textures had to share the same wrap and interpolation flags; instanced geometry and interleaved buffers were not supported — [README at v0.0.24](https://github.com/gkjohnson/three-gpu-pathtracer/blob/v0.0.24/README.md); compare [current README](https://github.com/gkjohnson/three-gpu-pathtracer/blob/main/README.md)
- WebGL-only items not yet ported: fog is listed under "Next Priority" for WebGPU; subsurface scattering, emissive-triangle NEE, per-object shadow-cast toggle, unlit materials, and the glTF extensions `KHR_materials_diffuse_transmission`, `KHR_materials_retroreflection`, `KHR_materials_volume_scatter` are also still to do — [Issue #777](https://github.com/gkjohnson/three-gpu-pathtracer/issues/777)

Documented API (WebGPU)
- API docs live on a docs site and as generated markdown in the repo — [API.md](https://github.com/gkjohnson/three-gpu-pathtracer/blob/main/src/webgpu/API.md); [docs site](https://gkjohnson.github.io/tools/docs/three-gpu-pathtracer/)
- Basic use: create a `THREE.WebGPURenderer` (import from `three/webgpu`), `await renderer.init()`, construct `new WebGPUPathTracer(renderer)`, call `setScene(scene, camera)` once, then `renderSample()` every frame — [README](https://github.com/gkjohnson/three-gpu-pathtracer/blob/main/README.md)
- Key properties and defaults: `maxBounces = 15`; `frameBudget = 250000` (path slots dispatched per `renderSample()` call, independent of resolution); `maxTransparentBounces = 5`; `maxSamples = 0` (0 = render forever; a denoiser only runs once the render has stopped, so it does nothing while this is 0); `filterGlossyFactor = 1`; `multipleImportanceSampling = true`; `clampDirect = 0`; `clampIndirect = 10`; `renderScale = 1`; `dynamicLowRes = true` with `lowResScale = 0.1`; `renderDelay = 500` ms; `fadeDuration = 500` ms; `synchronizeRenderSize = true`; `stableNoise = true`; `pause` — [API.md](https://github.com/gkjohnson/three-gpu-pathtracer/blob/main/src/webgpu/API.md)
- Methods: `setScene`, `setCamera`, `updateMaterials`, `updateTransforms`, `updateCamera`, `updateEnvironment`, `updateLights`, `setSize`, `reset`, `renderSample`, `setDenoiser`, `setUpscaler`, `setRandom`, `getSampleCountsAsync`, debug views (`renderDebugBounds`, `renderTextureAtlas`, `renderSampleDensity`), `dispose`. Geometry changes require `setScene` again because the BVH must be rebuilt, and geometry BVHs are built synchronously, so `setScene` blocks on large scenes — [API.md](https://github.com/gkjohnson/three-gpu-pathtracer/blob/main/src/webgpu/API.md)
- Samplers: `RANDOM_PCG`, `RANDOM_SOBOL`, `RANDOM_BLUE_DITHER` (default). Transmissive background modes: overlay (default), environment, transparent — [API.md](https://github.com/gkjohnson/three-gpu-pathtracer/blob/main/src/webgpu/API.md)
- Denoising: `OIDNDenoiser` takes `initUNetFromURL` from `oidn-web` and a weights URL as constructor arguments (so neither the library nor the weights are a hard dependency), supports guided (albedo+normal) and colour-only models, `maxTileSize` and adaptive `dynamicTile`; it is attached with `pathTracer.setDenoiser(...)` and runs once the render settles — [API.md](https://github.com/gkjohnson/three-gpu-pathtracer/blob/main/src/webgpu/API.md)
- Upscaling: `FSRUpscaler` wraps the `Upscaler` class from `@pmndrs/upscaler`, attached with `setUpscaler(...)`, so the path trace can run below canvas resolution — [API.md](https://github.com/gkjohnson/three-gpu-pathtracer/blob/main/src/webgpu/API.md)
- Environment: `BlurredEnvMapGenerator` produces a PMREM-prefiltered equirect copy to speed convergence; README notes MIS can be disabled and a blurred env map used when performance matters — [README](https://github.com/gkjohnson/three-gpu-pathtracer/blob/main/README.md)

Known issues named in the brief
- #777 "WebGPUPathTracer: Remaining features" — open, created 5 Jul 2026, last updated 29 Sep 2026. Tracks remaining work: an "upscale" toggle failure in the main demo, fog, SSS, emissive NEE, improved env sampling, floating-point artifacts when zoomed far out, BVH problems when different geometries share indices, leaf-cluster overruns on meshopt-quantized models, wavefront performance work (ray sorting, memory reduction), an "any hit" shadow-ray function, a command-line renderer and a benchmark tool (both unbuilt), and longer-term items such as bidirectional/spectral tracing, an R3F component, and OIDN support for DoF/transparency — [Issue #777](https://github.com/gkjohnson/three-gpu-pathtracer/issues/777)
- #826 "WebGPU: texture atlas repacks on every `updateMaterials()`" — created 21 Aug 2026, closed 26 Sep 2026 (labelled bug). Reporter measured 760–805 ms per `updateMaterials()` call with 9 texture maps during live editing, because the atlas hash was invalidated by its own packing and by uuid-sorted material order; related fix PR #830 was closed 23 Aug 2026 — [Issue #826](https://github.com/gkjohnson/three-gpu-pathtracer/issues/826); [PR #830](https://github.com/gkjohnson/three-gpu-pathtracer/pull/830)
- #868 "WebGPU: kernels fail to compile ('cannot index type RayData') after the first sample is rendered at 1 x 1" — open, created 30 Sep 2026 against v0.0.26, three r186.1, Chrome 152 and Edge on Windows 11 / RTX 4070. If the first sample is rendered at 1×1 (e.g. a hidden or collapsed canvas) and the size then grows, WGSL compilation fails and the tracer never recovers; workaround is to skip rendering while the target is tiny or to create a new tracer once the real size is known — [Issue #868](https://github.com/gkjohnson/three-gpu-pathtracer/issues/868)
- #829 (open, 22 Aug 2026): a user shipping OIDN on top of the WebGPU tracer notes that neither tracer exposes AOVs, so they rasterize albedo/normal with the same renderer; lists pitfalls (sanitize NaN/Inf but do not clamp HDR beauty; clamp albedo; decode normals; WebGPU readback row padding and row order; 2048 px tiles with 96 px overlap at 4K+) — [Issue #829](https://github.com/gkjohnson/three-gpu-pathtracer/issues/829)
- Other open requests relevant to interiors: custom ShaderMaterials (#747), area-light surface rendering (#618), bump-map support (#558), spotlights not reflecting in mirrors (#247), SSS (#271), light-sampling improvements (#515, #528) — [open issues](https://github.com/gkjohnson/three-gpu-pathtracer/issues)

Browser support
- The current library requires WebGPU with no WebGL fallback in the new tracer — [README](https://github.com/gkjohnson/three-gpu-pathtracer/blob/main/README.md)
- WebGPU availability per web.dev (article dated 25 Nov 2025): Chrome/Edge 113+ on Windows, macOS, ChromeOS; Chrome 121+ on Android 12+ (Qualcomm/ARM GPUs); Firefox 141+ on Windows and 145+ on macOS Tahoe 26 (ARM64 only); Safari 26 on macOS/iOS/iPadOS/visionOS 26. Linux support in Chrome and Linux/Android/Intel-Mac support in Firefox were described as in progress — [web.dev](https://web.dev/blog/webgpu-supported-major-browsers)

Render time
- No benchmark numbers are published in the README, API docs, changelog, or the issues/PRs searched; a "Benchmark tool" and "Evaluate performance" are still listed as to-do items — [Issue #777](https://github.com/gkjohnson/three-gpu-pathtracer/issues/777); [PR #713](https://github.com/gkjohnson/three-gpu-pathtracer/pull/713)
- The maintainer wrote on 26 Aug 2026 that there would still be room for performance improvements after the initial release — [Issue #777 comments](https://github.com/gkjohnson/three-gpu-pathtracer/issues/777)

### Inferences
- Rough lower-bound arithmetic from the documented default `frameBudget = 250000`: 1080p has 2,073,600 pixels, so 256 spp is ~531 M path slots = ~2,120 `renderSample()` calls; at one call per 60 Hz frame that is ~35 s (≈71 s at 30 Hz). 4K has 8,294,400 pixels, so ~2.12 B slots = ~8,490 calls = ~142 s at 60 Hz (≈283 s at 30 Hz). Real time is likely longer because in a wavefront tracer a path with several bounces needs several iterations, and shorter if `frameBudget` is raised on a strong GPU for an offline-style "render still" mode. Treat "tens of seconds for 1080p, a few minutes for 4K at 256 spp on a discrete GPU" as an unverified planning estimate that must be measured.
- Because the denoiser only runs after `maxSamples` is reached, a "photo" mode should set `maxSamples` (e.g. 64–256) rather than leave it at 0.
- #826 was closed two days before v0.0.25, so the atlas-repack fix is probably in the released build, but this was not verified against the release diff.
- #868 is directly relevant to a studio UI where the render canvas may be mounted hidden; guard against rendering at ≤ a few pixels.
- A v0.0.x library whose WebGPU path is under a week old, with its WebGL predecessor deprecated, is an adoption risk: pin the version, and expect API churn.
- The absence of the "same wrap/interpolation flags" and "no instancing" gotchas in the current README suggests the texture atlas and instance support removed those WebGL limits.

### Gaps
- No measured seconds for 1080p or 4K at 256 samples on any named GPU were found for either tracer; the figures above are arithmetic, not benchmarks.
- No authoritative statement was found on WebGPU status in Chrome on Linux or Firefox on Android as of October 2026 (latest primary source located is Nov 2025).
- Mobile behaviour (memory limits, thermal throttling) of the WebGPU tracer is undocumented beyond "Mobile support" being listed as implemented.
- Whether three.js `RectAreaLight` is consumed directly or only via `ShapedAreaLight` in the WebGPU build was not confirmed from the docs read.

## A2. Denoising in the browser: oidn-web

### Takeaway
The package is `oidn-web` in the repository pissang/oidn-web (not pmndrs — `github.com/pmndrs/oidn-web` returns 404); it is MIT-licensed, WebGPU-only, actively maintained (v0.4.0, 20 Aug 2026), runs Intel OIDN's U-Net as native WGSL compute, and needs a 0.6–7.7 MB weights download. No measured denoise times are published in the material read; the design target is ~16 ms of GPU work per tile.

### Cited Findings
- `https://api.github.com/repos/pmndrs/oidn-web` returns "Not Found" (checked 2 Oct 2026). The npm package `oidn-web` is developed at pissang/oidn-web: MIT, ~290 stars, created 10 Jun 2024, last commit 24 Sep 2026 — [pissang/oidn-web](https://github.com/pissang/oidn-web)
- npm versions: 0.3.0 (30 Jul 2024) … 0.3.5 (25 Jul 2025), 0.4.0 (20 Aug 2026, current `latest`) — [npm registry](https://registry.npmjs.org/oidn-web)
- The README states it is only available on browsers that support WebGPU — [oidn-web README](https://github.com/pissang/oidn-web/blob/main/README.md)
- Implementation: the OIDN U-Net runs directly on WebGPU via WGSL compute pipelines; uses half-float weights when the device has `shader-f16`, otherwise an FP32 path; pipelines compile asynchronously before init resolves. The repo's benchmark tooling compares against an earlier TensorFlow.js-based build — [oidn-web README](https://github.com/pissang/oidn-web/blob/main/README.md)
- Supports LDR and HDR input, optional albedo/normal auxiliary images, and GPU-buffer input/output on a shared `GPUDevice` to avoid CPU/GPU sync; a three-gpu-pathtracer example is linked — [oidn-web README](https://github.com/pissang/oidn-web/blob/main/README.md)
- Tiling: high resolutions are split into tiles, one tile in flight at a time; adaptive tile size starts at 432 px, never goes below 256 px, and targets about 16 ms of GPU work per tile — [oidn-web README](https://github.com/pissang/oidn-web/blob/main/README.md)
- Weights (.tza) are not bundled in the npm package; they come from the repo or RenderKit/oidn-weights. "Small" weights trade quality for speed, "large" the reverse — [oidn-web README](https://github.com/pissang/oidn-web/blob/main/README.md)
- Weight file sizes (from the Git LFS pointers in RenderKit/oidn-weights): `rt_hdr_alb_nrm.tza` 1,841,160 bytes (~1.8 MB); `rt_hdr_alb_nrm_small.tza` 641,480 bytes (~0.64 MB); `rt_hdr_calb_cnrm_large.tza` 7,698,439 bytes (~7.7 MB); `rt_hdr.tza` and `rt_ldr.tza` 1,830,792 bytes each — [RenderKit/oidn-weights](https://github.com/RenderKit/oidn-weights)
- three-gpu-pathtracer integrates it through `OIDNDenoiser` (PR #831), with `initUNetFromURL` and weights passed in by the app — [API.md](https://github.com/gkjohnson/three-gpu-pathtracer/blob/main/src/webgpu/API.md); [Issue #777](https://github.com/gkjohnson/three-gpu-pathtracer/issues/777)
- Remaining denoiser work listed upstream: remove an unneeded copy (needs oidn-web to provide a storage texture), support non-clean aux textures, and better handling of custom camera rays/distortion, transparency and depth of field (requires rendering albedo/normal textures) — [Issue #777](https://github.com/gkjohnson/three-gpu-pathtracer/issues/777)
- Related pmndrs projects: pmndrs/denoiser (OIDN ported to ONNX; MIT; created 6 Jul 2026; 7 stars; last push 10 Jul 2026) and its predecessor DennisSmolek/Denoiser (OIDN on TensorFlow.js; MIT; 53 stars). pmndrs/upscaler (WebGPU FSR port used by `FSRUpscaler`) has no SPDX-recognised licence per the GitHub API (`NOASSERTION`) — [pmndrs/denoiser](https://github.com/pmndrs/denoiser); [DennisSmolek/Denoiser](https://github.com/DennisSmolek/Denoiser); [pmndrs/upscaler](https://github.com/pmndrs/upscaler)

### Inferences
- From the 432 px starting tile and ~16 ms/tile target: 1080p is roughly 15 tiles and 4K roughly 45 tiles, i.e. on the order of 0.25 s and 0.75 s at one tile per 60 Hz frame if the target is met; slower GPUs shrink tiles and take longer. This is derived from design parameters, not a benchmark.
- Guided denoising (albedo + normal) is the default path in `OIDNDenoiser` (`auxWeightsUrl` is the required argument), so the default download is the ~1.8 MB guided model, or ~0.64 MB for the small variant.
- Since denoising makes 32–64 spp images presentable, it shifts the browser option's wall-clock time down substantially relative to the 256 spp arithmetic in A1.
- pmndrs/upscaler's licence should be checked by hand before depending on `FSRUpscaler`; the API reports no recognised licence.

### Gaps
- No published seconds-per-megapixel figures for oidn-web 0.4.0 were captured; the README's benchmark section describes a harness rather than results in the portion read.
- Behaviour on Safari/Firefox WebGPU implementations is not documented in the README.

## A3. bhouston/three-gpu-pathtracer-fidelity

### Takeaway
It is a two-day-old (created 1 Oct 2026) MIT test harness that renders each scene with Blender Cycles, the legacy WebGL tracer and the new WebGPU tracer at 4096 spp, then diffs and scores them; it does not yet publish a usable headline score against Cycles, and its own docs say the committed images predate the current pipeline and the checks so far are smoke tests.

### Cited Findings
- Repository created 1 Oct 2026, last push 2 Oct 2026, 21 commits, 1 star, MIT licence — [bhouston/three-gpu-pathtracer-fidelity](https://github.com/bhouston/three-gpu-pathtracer-fidelity)
- Purpose: validate the WebGPU path tracer against two references — Blender Cycles (independent production path tracer) and the established `WebGLPathTracer`. All three default to 4096 spp, seeded — [README](https://github.com/bhouston/three-gpu-pathtracer-fidelity/blob/main/README.md)
- It tests bhouston's fork of three-gpu-pathtracer (pinned as a submodule), not the npm release; the fork was last pushed 28 Sep 2026 — [README](https://github.com/bhouston/three-gpu-pathtracer-fidelity/blob/main/README.md); [bhouston/three-gpu-pathtracer](https://github.com/bhouston/three-gpu-pathtracer)
- Method: scene registry (`gi-*` global-illumination rooms, `khronos-*`/`x-*` glTF sample assets using the Khronos render-fidelity scenarios, `model-*` staged models with rect-area light rigs); headless rendering via dawn (WebGPU) and ANGLE (WebGL), each in its own child process; Blender 4.0+ via a Blender adapter; scoring/diffing/viewing with fidelity-kit; a `quality-gate` command fails when mean RMSE versus `webgl-legacy` regresses by more than a threshold (default 1%) — [README](https://github.com/bhouston/three-gpu-pathtracer-fidelity/blob/main/README.md)
- Render settings for comparability: explicit sRGB output with each scene's tone mapping and exposure, eight bounces, no denoising; Blender uses seed 1 with adaptive sampling disabled — [README](https://github.com/bhouston/three-gpu-pathtracer-fidelity/blob/main/README.md)
- Committed results: 43 scene folders (6 `gi-*`, 37 `khronos-*`, including Sponza, GlamVelvetSofa, SheenChair, glass and iridescence tests), each with `blender.avif`, `webgl-legacy.avif`, `webgpu-new.avif`; the metric/delta files are git-ignored and regenerated on demand — [results directory](https://github.com/bhouston/three-gpu-pathtracer-fidelity/tree/main/results)
- The viewer intro cautions that the two references are not identical to each other, so a WebGPU-vs-reference difference is most meaningful when the other reference agrees — [results/README.md](https://github.com/bhouston/three-gpu-pathtracer-fidelity/blob/main/results/README.md)
- Stated limits of the current results: the validation doc says the 16 spp Blender/WebGL checks on room, textured-box and transmission scenes showed matching framing and recognisable materials but visible brightness/transport differences, and describes them as "smoke tests, not a high-sample fidelity certification"; the README says committed images still come from the previous rendering pipeline and must all be regenerated — [rendering-integration-validation.md](https://github.com/bhouston/three-gpu-pathtracer-fidelity/blob/main/docs/rendering-integration-validation.md); [README](https://github.com/bhouston/three-gpu-pathtracer-fidelity/blob/main/README.md)
- Translation gaps between three.js and Cycles recorded by the harness: ambient lights and finite punctual-light cutoffs are ignored with warnings; custom shaders, non-physical light decay, blurred/GPU-only backgrounds and anamorphic DoF are unsupported; skin/morph pose matching and advanced glTF extensions still need visual validation; area lights and physical-camera DoF are translated via an optional adapter feature — [README](https://github.com/bhouston/three-gpu-pathtracer-fidelity/blob/main/README.md)
- Upstream three-gpu-pathtracer also ships its own "Model Viewer Fidelity Scene Comparisons" demo (`viewerTest`) — [three-gpu-pathtracer README](https://github.com/gkjohnson/three-gpu-pathtracer/blob/main/README.md)

### Inferences
- There is currently no citable number of the form "WebGPU tracer is within X% RMSE of Cycles"; the repo provides the apparatus, and a team could run it (or its `gi-room-*` scenes) to obtain one.
- The listed three.js→Cycles translation gaps (ambient lights, light cutoffs, decay) are exactly the parity problems a server-side Cycles pipeline for a three.js studio would face.

### Gaps
- The hosted viewer (three-gpu-pathtracer-fidelity.ben3d.ca) could not be read: the TLS certificate did not match the hostname at fetch time, so per-scene scores were not obtained.
- No aggregate WebGPU-vs-Cycles metric is committed to the repository.

## A4. Server-side alternative: headless Blender Cycles on cloud GPUs; how interior-design products deliver and price HD renders

### Takeaway
On an RTX 4090-class cloud GPU, Cycles renders a 1080p interior benchmark frame (Classroom, 300 samples) in roughly 7–12 s, and at 2026 marketplace prices (about $0.34–0.74/hour for a 4090) raw GPU cost is well under one US cent per 1080p frame; commercial interior tools all render in the cloud and sell it as subscription allowances (free 1K, paid 4K from about $7–$50/month, or roughly $2 per extra 4K image).

### Cited Findings

Cycles speed
- Blender Open Data, RTX 4090 with OptiX on Blender 5.2.0 (57 runs, verified 1 Oct 2026): median score ~11,571 samples/min; estimated per-frame times Classroom (1920×1080, 300 samples) 7.44 s, Junkshop (240 samples) 4.86 s, Monster (256 samples) 3.55 s. The page notes these estimates include a 19% buffer — [Renderjuice, citing Blender Open Data](https://www.renderjuice.com/gpus/rtx-4090-for-blender); raw data at [opendata.blender.org](https://opendata.blender.org/benchmarks/query/)
- SaladCloud benchmark (article dated 4 Sep 2025; Blender 4.5.0, Cycles with CUDA, 3,000+ nodes, 27 GPU models; scenes Classroom 1920×1080/300 spp, Monster 1024×1024/256 spp, Junkshop 2000×1000/240 spp): RTX 5090 ~340 frames/hour, RTX 4090 ~295 frames/hour; cost efficiency ~1,190 frames per dollar on RTX 4080 and >650 frames per dollar on RTX 4090; consumer GPUs were priced at $0.12–0.35/hour on that platform's batch tier — [Salad blog](https://blog.salad.com/blender-rendering-benchmark/)

Cloud GPU prices (2026)

- Blender's glTF importer (4.5 LTS manual) builds Principled-BSDF node graphs to replicate each glTF material as closely as possible; it supports core metal/rough PBR and, on import, `KHR_materials_pbrSpecularGlossiness`, `_clearcoat`, `_transmission`, `_unlit`, `_emissive_strength`, `_volume`, `_sheen`, `_specular`, `_anisotropy`, `_ior`, `_variants`, plus `KHR_lights_punctual`, `KHR_texture_transform`, `KHR_mesh_quantization`, `EXT_mesh_gpu_instancing` — [Blender 4.5 manual, glTF 2.0](https://docs.blender.org/manual/en/4.5/addons/import_export/scene_gltf2.html)

### Inferences
- Cost per image (GPU time only), using RunPod Secure Cloud RTX 4090 at $0.74/h = $0.000206/s: a 7.4 s Classroom-class 1080p render is ~$0.0015; allowing 20–40 s end-to-end for a warm worker (glTF import, BVH build, texture load, render, OIDN/OptiX denoise, encode) gives ~$0.004–0.008 per 1080p image. 4K has 4× the pixels, so ~30 s of rendering at the same sample count and ~45–90 s end-to-end, i.e. ~$0.01–0.02. Community/batch-tier pricing ($0.12–0.35/h) cuts this by half or more. Salad's ">650 frames per dollar" on a 4090 (~$0.0015/frame) is consistent with this.
- With OIDN or OptiX denoising, interior frames can typically use far fewer than 300 samples, so render time per frame can drop below the benchmark figures; conversely, real interiors lit mainly by small emitters or through glass converge more slowly than the benchmark scene. Neither effect was quantified by a source here.
- Cold starts dominate serverless cost and latency: container pull plus Blender start-up can exceed the render itself, so a warm pool or queue is needed for an interactive "Render" button.
- Competitor pricing implies users expect 1K/HD renders free and 4K as a paid tier; at roughly $2 per extra 4K image retail versus ~$0.01–0.02 GPU cost, server rendering has ample margin even at low utilisation.
- IKEA Kreativ is a photo-based reconstruction/compositing pipeline rather than a path-traced render of a modelled room, so it is not a direct precedent for either option.
- A glTF exported from the studio should avoid KTX2/meshopt (export PNG/JPEG/WebP textures, uncompressed or quantized meshes) for the Blender importer, and iridescence/dispersion would be lost.

### Gaps
- No primary source gives seconds per 4K interior frame with OIDN/OptiX denoise on a named cloud GPU; the 4K figures are scaled from 1080p benchmark data.
- The Blender Open Data site was not queried directly; the RTX 4090 figures come from an aggregator that cites it and adds a 19% buffer. Salad's scores (CUDA) are not comparable with OptiX scores.
- Coohom's and Planner 5D's per-plan render allowances could not be confirmed on their own pricing pages (dynamic content); the allowances quoted are from secondary sources.
- Homestyler's per-render price in USD could not be confirmed on the primary page.
- No source was found describing the render engines behind Homestyler or Planner 5D, or whether IKEA Kreativ renders server-side.
- Hyperscaler (AWS/GCP/Azure) GPU prices and other engines (e.g. headless three.js/dawn, LuxCore, V-Ray cloud) were not researched within the call budget. Note: the fidelity harness shows three-gpu-pathtracer itself can run headless on a server through dawn — [README](https://github.com/bhouston/three-gpu-pathtracer-fidelity/blob/main/README.md).

## A5. Trade-offs: browser path tracing vs server Cycles

### Takeaway
The browser route costs nothing per render and keeps exact three.js material parity but depends on the user's GPU and a WebGPU browser and rests on a library released days ago; the server route gives uniform quality and speed on any device for roughly a cent per 4K image but adds queueing, infrastructure, and a three.js→Cycles translation layer where lighting and some material extensions do not map one-to-one.

### Cited Findings
- Device dependence (browser): the new tracer requires WebGPU — [three-gpu-pathtracer README](https://github.com/gkjohnson/three-gpu-pathtracer/blob/main/README.md); WebGPU coverage has platform holes (Firefox on Linux/Android/Intel Macs and Chrome on Linux were in progress as of Nov 2025; Android needs version 12+) — [web.dev](https://web.dev/blog/webgpu-supported-major-browsers)
- Maturity (browser): WebGPU tracer first released 28 Sep 2026; an open bug can permanently break the tracer after a 1×1 first frame; unreleased fixes include a memory leak on every reset — [Issue #868](https://github.com/gkjohnson/three-gpu-pathtracer/issues/868); [CHANGELOG](https://github.com/gkjohnson/three-gpu-pathtracer/blob/main/CHANGELOG.md)
- Material parity (browser): the tracer consumes three.js `MeshStandardMaterial`/`MeshPhysicalMaterial` directly, so the still uses the same scene graph as the live view; custom `ShaderMaterial`s are not supported (open request #747) — [README](https://github.com/gkjohnson/three-gpu-pathtracer/blob/main/README.md); [Issue #747](https://github.com/gkjohnson/three-gpu-pathtracer/issues/747)
- Scene-update cost (browser): geometry changes need a full `setScene` with synchronous BVH build; material updates were measured at 760–805 ms before the atlas fix — [API.md](https://github.com/gkjohnson/three-gpu-pathtracer/blob/main/src/webgpu/API.md); [Issue #826](https://github.com/gkjohnson/three-gpu-pathtracer/issues/826)
- Denoise download (browser): 0.64–7.7 MB of OIDN weights, WebGPU only — [oidn-web README](https://github.com/pissang/oidn-web/blob/main/README.md); [RenderKit/oidn-weights](https://github.com/RenderKit/oidn-weights)
- Material parity (server): Blender imports most core glTF PBR extensions into Principled BSDF but not iridescence, dispersion, KTX2 or meshopt per its documented import list — [Blender 4.5 manual](https://docs.blender.org/manual/en/4.5/addons/import_export/scene_gltf2.html); the fidelity harness documents that ambient lights, light cutoffs, non-physical decay and custom shaders do not translate to Cycles, and that even matched scenes show visible brightness/transport differences at low sample counts — [fidelity README](https://github.com/bhouston/three-gpu-pathtracer-fidelity/blob/main/README.md); [validation doc](https://github.com/bhouston/three-gpu-pathtracer-fidelity/blob/main/docs/rendering-integration-validation.md)
- Speed and cost (server): ~7.4 s per 1080p/300-sample interior benchmark frame on RTX 4090 OptiX; $0.34–0.74/h for that GPU class on RunPod; >650 frames per dollar measured on a distributed cloud — [Renderjuice/Blender Open Data](https://www.renderjuice.com/gpus/rtx-4090-for-blender); [RunPod pricing](https://www.runpod.io/pricing); [Salad blog](https://blog.salad.com/blender-rendering-benchmark/)
- Market practice: Coohom, Homestyler and Planner 5D all sell cloud-rendered stills by resolution tier — [Coohom pricing](https://www.coohom.com/pricing); [Homestyler pricing](https://www.homestyler.com/pricing); [Planner 5D pricing](https://planner5d.com/pricing)

### Inferences
- Browser: zero marginal cost, no upload of the user's scene, instant progressive feedback, identical materials; but time and success vary with the device (integrated GPUs and phones may take minutes or fail on memory), the tab must stay open, and 4K output stresses GPU memory.
- Server: predictable time and quality on any device including phones, output above 4K is feasible, renders can continue in the background; but needs job queueing, autoscaling/warm workers, asset upload of the glTF, per-render cost (small), and a maintained translation layer (lights in physical units, tone mapping/exposure matching, environment map orientation).
- "What you see is what you get" risk is highest on the server path: users compose in three.js rasterization and receive a Cycles image whose light intensities and tone mapping may differ unless calibrated; the browser tracer shares three.js tone mapping and material definitions.
- A hybrid is plausible: browser path tracing as a free preview/HD tier where WebGPU is available, with a server tier for 4K+ and for devices without WebGPU. A third option suggested by the fidelity harness is running the same three-gpu-pathtracer headless on a server GPU (dawn), which would keep material parity while removing device dependence; this was not benchmarked by any source found.

### Gaps
- No head-to-head timing of the same interior scene in three-gpu-pathtracer versus Cycles on the same GPU was found.
- No data on failure rates or memory ceilings of WebGPU path tracing on integrated/mobile GPUs.
